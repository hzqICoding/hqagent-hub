## 1. 文档目的

`docs/施工方案.md` 定义了产品、架构和协议；`docs/前端开发与验收方案.md` 把桌面前端拆成了可独立开工的工作包；`docs/OTA升级架构设计.md` 定义了升级链路。三份文档解决了"做什么"，但没有解决"谁做、按什么顺序做、哪些能同时做、包与包之间靠什么对齐"。

本文档补上这一层，作为一期的开工调度依据。它回答四个问题：

1. 一期拆成哪几个工作包，每个包的边界、交付物和验收标准是什么。
2. 每个包由哪个执行方承担，怎么派活。
3. 包与包之间冻结哪些契约，冻结点没到之前谁可以先开工。
4. 现有三份文档里有哪些互相打架或没写的地方，本轮怎么裁决。

本文档不重复已有内容。前端的页面清单、主题体系、验收矩阵一律引用 `docs/前端开发与验收方案.md`；升级状态机、Target、签名策略一律引用 `docs/OTA升级架构设计.md`；角色、能力、任务、事件的语义一律引用 `docs/施工方案.md`。

## 3. 核心事实（先理解，否则会做错）

### 3.1 关于可复用资产（已实测）

- `E:\OtherPro\HQDroidDeck-Desktop\internal\update` 共 **1619 行，全部使用 Go 标准库，没有任何 Wails 依赖**。代码中的 `runtime.` 全部是 `runtime.GOOS` / `runtime.GOARCH`，不是 Wails runtime。

- `E:\OtherPro\OTA-Platform` 与 `E:\OtherPro\HQDroidDeck-Desktop` 均存在且结构与文档描述一致。HQDroidDeck 的 Go 模块名为 `github.com/ua/device-assistant`，Go 1.26。

### 3.2 关于当前文档状态

- 桌面前端已经具备"不等后端即可开工"的完整条件（`UiGateway` + `MockGateway` + Fixture + 主题体系 + 页面清单 + 验收矩阵），是唯一一个可以在协议冻结当天就全速推进的包。
- Local Hub 是所有其他包的依赖，但它自己**没有工作包级文档**，模块职责散落在 `docs/施工方案.md` §5.3、§6、§7、§8 四处，缺 SQLite schema、事件存储与补发策略、进程模型、本机鉴权。

### 3.3 关于并行度

一期八个包中，W0（协议包、仓库骨架和本机接入契约）是共同串行前置。FZ-1 完成后，W1、W4、W5 和 W6 的共享模块抽取可以并行；Claude 同期完成 FZ-2，随后解锁 W2/W3。各线通过版本化协议、固定 baseCommit 和 §7 的冻结/就绪门交互，不依赖同一工作目录里的未提交代码。

## 4. 一期范围与非目标

### 4.1 一期必须达成

1. 桌面应用可以安装、启动、自发现本机 Claude 与 Codex，并展示能力清单。
2. 用户可以在桌面端创建和切换 Team Profile，把 8 个内置角色绑定到任意已安装 Agent。
3. 从桌面端提交一条需要多角色协作的任务，`architect` 出方案、`general_implementer` 实现、`reviewer` 独立复核，全程走统一事件流。
4. 写任务在独立 git worktree 中执行，越界修改能被 `git diff --name-only` 检出并拦截。
5. 危险操作触发审批，未批准不执行。
6. 首选 Agent 离线时命中备用链，并在界面上显示降级原因和来源。
7. Local Hub 重启后能恢复未完成任务和已登记会话。
8. 整包 OTA 闭环：检查、续传下载、SHA-256 + Ed25519 验签、任务排空、SQLite 一致性备份、独立 Updater 安装、重启回执、健康检查和自动回退。

### 4.2 一期明确不做

- 云端 Control Plane、手机 PWA、设备配对、推送通知。
- 支付、套餐、授权续期。
- 匿名埋点上传（本地生成和预览可保留，不接云端）。
- 榜单、推荐、模板市场。
- macOS 与 Linux 打包（组件必须跨平台友好，但只验收 Windows）。
- Gemini CLI、GLM、K3 适配器。
- Antigravity Adapter 不进入关键路径，见 §8 D5。

### 5.1.1 Git 与 worktree 启动模型

W0 必须先完成 Git 初始化和基线提交，再派发任何并行包：

```text
main                         稳定主线
integration/phase1           一期集成分支
work/w0-protocol
work/w1-hub
work/w4-frontend
work/w5-shell
work/w6-updatekit
```

每条执行线使用独立物理目录，例如：

```text
E:\OtherPro\HQAgent-Hub-worktrees\w1-hub
E:\OtherPro\HQAgent-Hub-worktrees\w4-frontend
E:\OtherPro\HQAgent-Hub-worktrees\w5-shell
E:\OtherPro\HQAgent-Hub-worktrees\w6-updatekit
```

要求：

- FZ-1 必须对应一个已提交的 Git SHA，并记录在 `.hqagent/INTERFACES.md`。
- 每个任务文件记录 `taskId`、`owner`、`baseCommit`、`branch`、`worktreePath`、`allowedPaths`、验收命令和 handoff 文件。
- 多个 Agent 禁止共用同一工作目录，即使它们写不同路径也不例外。
- 合并统一进入 `integration/phase1`；共享根配置和 Composition Root 由当批 Integrator 修改，普通工作包通过 handoff 请求变更。
- W3 的产品内 Worktree Manager 未完成前，使用 Git 命令或固定脚本创建和校验 worktree，不能依赖尚未实现的产品能力。

```text
artifacts              artifact_id, task_id, node_id, kind, path, sha256, created_at
idempotency_records   key, route, request_hash, response_json, expires_at
```

3. **事件总线**：`seq` 由与业务状态同一事务写入的 `events` 表产生，提交成功后再推送，保证重启和并发生产者下的顺序一致。实现分页 `GET /api/v1/events?after={seq}` 与 WS 推送；相同 `event_id` 幂等。游标已过期时返回 `EVENT_CURSOR_EXPIRED` 和最新 Snapshot 入口，前端重新 bootstrap，不能静默丢事件。
4. **本机鉴权**：HTTP 校验 `Authorization: Bearer <startup-token>`；严格限制 CORS/Origin，只允许打包后的 Tauri Origin 和显式开发 Origin。`POST /api/v1/auth/ws-ticket` 使用 Bearer 换取 30 秒有效、单次使用的 WS Ticket，原生 WebSocket 使用 Ticket 握手。Token/Ticket 不写访问日志。
5. **API 门面**：Local Hub 是 Vue 唯一 Base URL。W1 实现鉴权、包络、路由装配、bootstrap/events/settings/update-proxy 等基础能力；W2/W3 通过预先冻结的 Port 注入 Agent、Team、Task、Session 和 Approval Handler。W1 自身不以假实现宣称全部业务路径完成，OpenAPI 全路径完成度在 RD-1 验收。
6. **Update Agent 代理**：Local Hub 读取仅当前用户可读的 `runtime/update-agent.json`，通过 `update-agent.internal.v1.yaml` 调用 W6；对 Vue 继续暴露 `/api/v1/updates/**`。Update Agent 通过内部事件入口提交更新事件，由 Hub 分配全局 `seq` 并持久化。
7. **bootstrap 聚合接口**：一次返回 Agent 概况、默认 Profile、未读审批数、更新状态摘要、协议版本和 Feature Availability；依赖包未就绪时返回明确 unavailable 原因，不伪造空成功。

| W6 | `E:\OtherPro\HQUpdateKit/**`、`apps/update-agent/**`、`apps/updater/**`；HQDroidDeck 迁移分支中仅更新模块接入路径 | `packages/protocol/generated/go/**`、HQDroidDeck 原更新实现 |
| W7 | `packaging/**`、`build/**`、`scripts/build/**`、`scripts/release/**`、`scripts/e2e/**` | 全部产物目录 |

共享根文件（根 Lockfile、CI、Workspace 配置、Composition Root）由当前批次的 `integrator` 统一修改。各工作包需要新增依赖或接线时写 handoff，由 Integrator 在 `integration/phase1` 合并；不得让两个 worktree 同时直接改同一共享文件。

除 W0 协议负责人外，任何包都不得直接修改 `packages/protocol/`。需要改协议的，走 §7 的变更流程，不允许在自己端偷偷增加同名兼容字段。

## 7. 契约冻结点与实现就绪门

冻结点用于固定契约，就绪门用于确认真实实现已经可联调。二者不能混用。每个冻结点记录协议版本、日期和 Git SHA；每个就绪门记录验证命令、结果和产物版本。

| 门 | 类型 | 内容 | 解锁范围 | 变更代价 |
| --- | --- | --- | --- | --- |
| **FZ-1** | 契约冻结 | 协议 v0.1、Schema/OpenAPI/Event/Error、原子 Fixtures、`hub.json/update-agent.json`、HTTP Bearer + WS Ticket、Local Hub 单一门面、当前用户 NSIS/目录/版本边界 | W1、W4、W5、W6 抽取并行开工 | 高。删除/重命名字段或改变进程边界必须全体评审 |
| **FZ-2** | 契约冻结 | Adapter Port 的方法签名、Session 生命周期、能力枚举、取消/审批/事件映射规则 | W2、W3 正式实现 | 中。主要影响 W2/W3 和任务事件 |
| **RD-1** | 实现就绪 | Local Hub 鉴权、bootstrap/events、WS Ticket、Update Proxy、drain/backup 端口可运行；Fake Handler 可完成契约测试 | W4 F5、W5 联调、W6 drain/update 集成 | 不是契约变更；未通过则实现继续修复 |
| **RD-2** | 实现就绪 | Claude/Codex Adapter、Role Resolver、任务/Session/审批闭环可运行 | INT-2 和 W7 最终打包验收 | 不是契约变更 |

**协议变更流程**：任何包发现协议有问题 → 在 `.hqagent/handoffs/` 写变更请求（问题、影响面、建议改法、兼容性和受影响 Fixture）→ Claude 起草 → Codex 做实现可行性复核、前端负责人做消费方复核 → 用户/产品负责人批准破坏性变更 → 更新 `packages/protocol` → 重新生成三份绑定 → 记录新 Git SHA → 通知受影响包。追加可选字段按 minor 兼容处理，不要求所有工作包停工；删除、重命名或语义变化才需要重新冻结。

## 8. 本轮裁决

以下十项是核对三份文档和开工边界后确定的裁决。FZ-1 以本节为准；后续如改变其中的进程、安全、安装或协议边界，必须重新评估受影响工作包。

### D1 本地更新接口：以 OTA 文档为准，前端在 Gateway 层做映射

- **修订前冲突**：前端方案曾只有 2 条动作级更新路径，而 OTA 方案定义 9 条细路径。
- **裁决**：Vue 看到的 Local Hub 公共 API 采用 OTA 文档的 9 条细路径（check / download / cancel / install / defer / state / result / result:acknowledge / releases）。前端 `UiGateway.controlUpdate(action)` 保持不变，由 `LocalHubGateway` 映射到这些路径。Local Hub 再通过 `update-agent.internal.v1.yaml` 调用 W6，Update Agent 不向 Vue 暴露第二个 Base URL。
- **理由**：细路径便于鉴权、审计和测试；单一门面避免前端管理两个端口、两个 Token 和两条事件序列。

### D2 本地与云端 API 命名空间分离

- **修订前冲突**：施工方案原 §10 的云端路径与前端 §13.2 的本地路径大量同名（`/api/v1/tasks` 等），但语义不同——云端是中转与队列，本地是真实执行。施工方案现已拆为 §10.1 本地、§10.2 云端、§10.3 OTA。
- **裁决**：路径都保留 `/api/v1`，但**两套 OpenAPI 分开生成**（`local-hub.v1.yaml` 与二期的 `control-plane.v1.yaml`），共享 `packages/protocol/schema/` 的领域模型，不共享路径层类型。本地只监听 `127.0.0.1`，云端只走域名。
- **理由**：领域模型必须共享（否则二期 PWA 又要重定义一遍 Task），但路径与包络语义不同，强行合并会在二期造成隐蔽 bug。

### D3 本机 Hub 发现与鉴权（修订前缺失）

- **缺口**：原文档没有说明前端如何发现 Hub、Update Agent 如何接入，也忽略了浏览器/WebView 原生 WebSocket 不能自定义 `Authorization` Header。
- **裁决**：Hub 随机高位端口、仅监听 `127.0.0.1`、启动 Token 每次轮换、`hub.json` 原子写入且 ACL 仅当前用户可读。HTTP 使用 Bearer；WebSocket 先以 Bearer 调 `POST /api/v1/auth/ws-ticket` 获取 30 秒单次 Ticket。严格限制 CORS/Origin/CSP，禁止远程页面导航。Update Agent 使用独立 `update-agent.json` 和内部 Token，只由 Local Hub/W5 读取。
- **理由**：该方案兼容标准 WebView，并明确安全边界。ACL/Token 用于阻止其他用户、普通网页和误调用，不承诺抵御已拥有当前用户权限的恶意进程。

### D4 状态枚举与事件字典对齐

- **修订前冲突**：前端 §13.5 的 `TaskStatus` 枚举缺少等待输入、阻塞和恢复等状态，施工方案 §8.3 的事件也没有到状态的明确映射；`task.claimed` 等事件不应被误当作状态值。
- **裁决**：以协议包 `events/event-dictionary.md` 为唯一事实源，给出"事件 → 状态迁移"表。前端枚举不足的部分补齐，多出的部分保留（`unknown` 是必要的前向兼容值）。
- **理由**：前端要靠事件驱动状态机，映射关系不明确会导致界面状态与 Hub 不一致。

### D5 Antigravity Adapter 移出一期关键路径

- **问题**：Antigravity 走 sidecar + agentapi，是原首发列表里唯一“接入方式未经实测”的 Adapter（施工方案 §7.1 把 Sidecar 排在可靠性第 4 级）。验证“更换 Agent 后无需修改工作流代码”可先用 Claude + Codex 两个 Agent 互换角色达成。
- **裁决**：一期关键路径只做 Claude 与 Codex 两个适配器。Antigravity 的**调研与规范照写**，实现排在 W2 末尾，达标则并入，不达标则以 `incompatible` 状态展示能力缺口，不阻塞任何验收项。
- **理由**：不能让可控性最低的依赖卡住整条主线。角色-Agent 解耦的验证价值来自"能换"，不来自"换成哪一个"。
- **影响**：`docs/施工方案.md` 的一期 M1/M2 与验收标准同步改为 Claude + Codex 技术闭环；`frontend_implementer` 一期可以由 Codex 承担并保留可切换绑定。Antigravity/Gemini Adapter 进入 Phase 1.1，不阻塞 Phase 1，但在对外宣传“三 Agent 联动”前必须完成。

### D6 Local Hub 维持 Python，但增加“可由安装器安全升级”的硬约束

- **风险**：Python 常驻服务 + PyInstaller 打包，与 OTA 完整安装包升级存在天然摩擦（文件占用、启动慢、目录体积）。
- **裁决**：维持 Python，并增加四条硬约束：onedir 打包、运行期不写安装目录、Hub 可在 15 秒内干净停止、升级前由 Hub 执行 WAL checkpoint 和 SQLite Backup。迁移默认向前兼容，不强制 Down Migration；回滚根据 `rollbackCompatible` 读取备份恢复。
- **理由**：保留 SDK 生态与开发效率，同时把整包升级和数据库恢复变成可验证流程。

### D7 Session 按任务血缘管理，不按角色全局复用

- **问题**：`workspace + role + agent` 唯一映射会让无关任务和并发任务共享外部会话，产生上下文污染、取消冲突和 reviewer 隔离失效。
- **裁决**：本地 `session_id` 关联 task/node/purpose/parent/reusePolicy；新任务默认新会话，只有明确继续操作或显式 `resume_session_id` 才恢复。共享项目知识通过 `.hqagent` 文档和任务 Handoff 注入。
- **理由**：持久化会话的目标是“可准确续接”，不是“所有任务永远使用一个聊天线程”。

### D8 Windows 当前用户 NSIS 与备份回滚

- **问题**：原方案同时使用“NSIS 安装”和“直接整包替换”，且未决定安装权限、程序目录和数据库回滚方式。
- **裁决**：Phase 1 使用当前用户级 `windows-nsis`，程序安装到 `%LOCALAPPDATA%\Programs\HQAgent-Hub\`，数据写 `%LOCALAPPDATA%\HQAgent-Hub\`。Updater 运行验签后的完整 NSIS Installer，保留上一版本恢复材料；健康检查通过前维持维护模式，失败时恢复程序和升级前数据库备份。
- **理由**：默认无需 UAC，符合当前用户 Agent 登录环境，也让程序文件与用户数据生命周期解耦。

### D9 HQUpdateKit 必须由两个产品共同依赖

- **问题**：只把 HQDroidDeck 更新代码复制到 HQAgent-Hub，不会消除分叉；把 `internal/update` 放进两个独立 Go Module 还会触发 Go Internal 可见性限制。
- **裁决**：建立独立版本化 `HQUpdateKit`，公共代码使用可导入 package，Update Agent/Updater 命令位于同一 Module；HQAgent-Hub 和 HQDroidDeck-Desktop 都锁定版本依赖。
- **理由**：只有两个产品消费同一版本化模块，安全修复和安装策略改动才能真正同步。

### D10 并行开发使用独立 worktree，协议 DTO 与 UI 场景分层

- **问题**：路径所有权不能防止多个 Agent 在同一工作目录争用 Git Index、Lockfile 和构建产物；同时 `UiGateway` 与 UI Scenario 不属于可由协议 Schema 直接生成的内容。
- **裁决**：W0 初始化 Git、集成分支和每包 worktree；FZ-1 记录 Commit SHA。自动生成范围仅限协议边界 DTO/API 类型，`UiGateway`/ViewModel 手写。协议目录保存原子 Fixture，前端目录保存引用这些 Fixture 的组合场景。共享根文件由 Integrator 修改。
- **理由**：物理隔离解决并行安全，分层事实源解决代码生成与 Mock 可维护性。

## 10. 跨包联调剧本

三次集成各有明确的失败判据，不通过不进下一批次。集成由 Claude 主持，逐项对照记录到 `.hqagent/handoffs/`。

### INT-1 本地空跑闭环（批次 3 出口）

参与：W1 + W4 + W5。

```text
启动桌面应用
→ Tauri 拉起 hqagent-core.exe
→ 前端从 invoke('get_hub_endpoint') 拿到 baseUrl 与 token
→ LocalHubGateway 调 GET /api/v1/bootstrap 成功
→ 通过 Bearer 获取一次性 WS Ticket 并建立事件流
→ Agents 页展示真实发现结果（Claude / Codex 的真实版本与登录状态）
→ WS 连上，杀掉 Hub 后自动重启并按 seq 补事件
```

失败判据：任何一步需要人工改端口、关鉴权、改前端页面代码。

### INT-2 双 Agent 协作闭环（批次 4 中段）

参与：W1 + W2 + W3 + W4。

```text
用默认 Profile（Claude=orchestrator/architect/reviewer，Codex=general_implementer/tester）
→ 提交一条真实小需求
→ architect 产出方案与验收标准
→ general_implementer 在独立 worktree 实现
→ 触发一次 git_push 审批，在界面上拒绝，任务进入 blocked/等待重规划且命令未执行
→ 用户选择重试并批准，reviewer 用独立 Session 复核真实 diff
→ 切换到第二套 Profile（Codex 承担全部角色），同一工作流代码不修改即可跑通
→ 手动停掉 Codex，验证 fallback 命中并显示降级原因
```

失败判据：工作流代码里出现任何厂商名硬编码；reviewer 复用了 implementer 的 Session；越界写入未被拦截。

### INT-3 升级闭环（批次 4 末）

参与：W1 + W5 + W6 + W7。

```text
安装 0.1.0 → 发布 0.1.1 到 beta
→ 应用检查到更新并下载（中途取消一次再续传）
→ 验签通过；篡改包重试一次，必须被拒
→ 启动一个长任务后触发安装，验证进入排空而非直接装
→ 排空完成并生成完整 waitPids/数据库备份
→ Update Agent 退出 → Updater 等全部进程退出 → 运行当前用户 NSIS → 重启 → 结果回执
→ 人为让健康检查失败，验证回退到 0.1.0 且任务、Session、Profile、配置不丢
```

失败判据：升级过程中丢任何一条未完成任务或会话记录。

| 风险 | 影响 | 缓解 |
