## 1. 项目概述

### 1.1 项目名称

`HQAgent-Hub`

### 1.2 产品定位

HQAgent-Hub 是一个“本地多 Agent 控制中心 + 远程控制云服务”。用户在自己的电脑上安装 Agent Hub，由它统一发现、启动、续接和管理 Codex、Claude Code、Gemini CLI、Google Antigravity、GLM、K3 以及后续第三方 Agent；用户可以通过手机 PWA、网页或桌面客户端远程下达任务、审批操作、查看进度并接收结果。

产品坚持本地优先：代码仓库、Agent 登录凭据、API Key、构建环境和主要执行过程默认留在用户电脑；VPS 只负责用户授权、设备绑定、任务中转、状态同步、通知、授权套餐和必要的加密元数据存储。

### 1.3 当前痛点

1. 不同 Agent 彼此独立，缺少明确的主从调度、职责边界和统一任务协议。
2. Claude 调用 Codex 时容易新建会话，导致重复理解项目和上下文丢失。
3. Claude 不能直接控制 Antigravity/Gemini 桌面会话，也不能统一收集执行结果。
4. 多个 Agent 同时修改同一工作目录时容易产生文件覆盖和 Git 冲突。
5. 当前缺少手机端统一入口、远程审批、断线恢复和完成通知。
6. 现有多 Agent 工具通常偏向“同时打开多个终端”，难以满足长期会话、自动交接和商业授权要求。

## 2. 已确认事实、假设与待确认项

### 2.1 已确认事实

- 首发运行环境为 Windows。
- 当前电脑已安装：
  - Codex CLI `0.147.0`
  - Claude Code `2.1.261`
  - Gemini CLI `0.50.0`
  - Antigravity Desktop `2.11.0`
- 用户已有 VPS、域名和 FRP 服务。
- 用户已有可运行的通用 `OTA-Platform`，支持 Product/Target/Release/Artifact、stable/beta、Ed25519、制品不可变、发布晋升和渠道回滚；HQDroidDeck-Desktop 已有完整 Go 客户端升级链路。
- 当前用户的默认团队配置：Claude 负责需求、设计、架构、审核和总调度；Antigravity/Gemini 负责前端；Codex 负责前端之外的实现、测试和工程任务。
- 不同用户拥有不同的 Agent 组合和角色偏好，产品必须允许一个 Agent 承担多个角色、一个角色配置多个候选 Agent，并支持全局、项目和单次任务覆盖。
- 产品后续需要支持其他用户安装、远程控制、授权和付费使用。

### 2.2 当前方案假设

- Phase 1 先完成 Windows 本地技术闭环，供个人自用和开发验收，不依赖 VPS、手机端或多租户服务。
- Phase 2 的手机端优先采用 Vue 3 PWA，后续按需要使用 Capacitor 打包 Android/iOS 应用。
- Phase 2 的商业用户不需要自行配置 FRP；本地 Agent Hub 主动通过加密 WebSocket 连接云端。
- 用户自行拥有并登录各 Agent，或者在本地配置自己的 API Key，即 BYOA/BYOK 模式。
- 云端默认不保存完整源代码，不提供模型账号和模型额度转售。

### 2.3 待确认项

- VPS 的操作系统、CPU、内存、磁盘、现有 Docker/Nginx/FRP 配置。
- 正式使用的域名或子域名，例如 `agent.example.com`。
- 第一阶段后端选用 FastAPI 还是 NestJS；本方案暂按 FastAPI 设计。
- 支付渠道：微信支付、支付宝、Stripe 或其他平台。
- GLM、K3 等首批扩展 Agent 的准确产品、CLI/API 名称和鉴权方式。
- 匿名产品分析是否在内测阶段默认关闭，以及正式运营地区的隐私政策、数据保留期限和用户同意文案。

## 3. 建设目标与边界

### 3.1 Phase 1 / P0：Windows 本地技术闭环

1. Windows Agent Hub 自动发现 Claude 与 Codex，以统一 Agent 实例和能力清单登记。
2. 用户在桌面端创建 Team Profile，将 `orchestrator`、`architect`、`reviewer`、`frontend_implementer`、`general_implementer`、`tester` 等角色绑定到任意已安装 Agent。
3. 工作流只引用角色，不在业务代码中写死 Claude、Codex、Gemini 等供应商名称；Role Resolver 支持任务、项目、全局、能力和备用链解析。
4. 桌面端可以选择项目和 Team Profile、发送本地任务，并按统一 `seq` 查看进度、问题、审批和结果。
5. 保存本地 Session 与 Claude `session_id`、Codex `thread_id` 的显式映射；新任务默认新会话，只有明确继续或传入 `resume_session_id` 才恢复旧会话。
6. Claude 与 Codex 可以按不同 Team Profile 互换角色，证明工作流与 Agent 品牌解耦。
7. 危险命令、删除、迁移、部署、`git push` 等操作进入本地审批，不经批准不能执行。
8. 每个写任务使用独立 Git worktree、分支和固定 `baseCommit`，并对 `allowed_paths` 做越界校验。
9. 桌面端从第一期支持 `system/light/dark`、多 Palette 和可访问性设置，页面可先通过 MockGateway 完整验收，再切 LocalHubGateway。
10. 建立 Windows 当前用户级 NSIS 整包 OTA 闭环：stable/beta 检查、续传下载、SHA-256/Ed25519 验签、任务排空、SQLite 一致性备份、独立 Updater 安装、重启回执、健康检查和自动回滚。

### 3.2 Phase 1.1：三 Agent 自用增强

- 完成 Antigravity Sidecar/`agentapi` 的实测适配；无法满足契约时显示 `incompatible` 和能力缺口，不伪装完成。
- 接入 Gemini CLI headless JSONL 与显式会话续接，作为 Antigravity 前端角色的备用方案。
- 跑通“Claude 设计/架构/审核 + Codex 通用实现 + Antigravity/Gemini 前端实现”的默认三 Agent Team Profile。
- 增加本地匿名事件生成、字段预览、关闭开关和本地模板统计，但不上传云端。
- 完善诊断包、崩溃恢复和 Adapter 兼容矩阵。

### 3.3 Phase 2 / P1：远程控制与商业闭环

- 云端 Control Plane、手机 PWA、设备配对、远程任务、审批、通知、离线队列和断线补传。
- Team Profile 加密同步、用户可选匿名分析上传、角色/组合榜单、场景模板和推荐服务。
- 套餐、授权、支付回调、订阅、设备限制和远程注销。
- Web Push/FCM、代码 Diff/日志/测试结果查看、定时任务和自动巡检。
- OTA 百分比灰度、生产密钥轮换和 Adapter 独立升级；自动健康回滚属于 Phase 1，不后移。
- 手机与本机 Runner 的端到端加密和商业发布合规工作。

### 3.4 Phase 3 / P2：跨平台与生态

- macOS、Linux 支持。
- GLM、K3 等更多插件式适配器，A2A/MCP 插件规范和市场。
- 团队成员、角色权限、共享项目、审计与企业私有部署。
- 基于成功率、稳定性、返工率和用户评价的个性化推荐；热门度和效果评分分开展示。
- 云端执行节点和混合调度。

### 3.5 非目标

- Phase 1 不建设 VPS Control Plane、手机 PWA、支付、公开榜单或推荐服务。
- 产品不在 VPS 上直接运行大规模代码构建，也不为每个用户托管完整 Agent 沙箱。
- 产品不转售 Claude、Codex、Gemini 等模型额度。
- 正式适配器不依赖鼠标和窗口坐标控制 Agent GUI。
- Phase 1 只要求 Claude 与 Codex 两个适配器；Antigravity/Gemini 在 Phase 1.1 完成。

## 5. 核心模块

### 5.1 手机端/PWA（Phase 2）

首发功能：

- 账号登录、设备绑定和设备在线状态。
- 项目列表、会话列表和新建任务。
- 选择 Team Profile、目标角色，必要时对本次任务临时指定具体 Agent。
- 查看当前角色分工、实际路由结果、备用 Agent 和能力缺口。
- 查看热门组合、场景模板和推荐理由，并可一键复制为自己的团队配置。
- 实时进度、工具调用、问题、审批和最终结果。
- 暂停、取消、继续、重试和追加指令。
- 任务完成、失败和等待审批通知。

建议技术栈：`Vue 3 + TypeScript + Vite + PWA`。

### 5.2 云端 Control Plane（Phase 2）

职责：

- 用户、设备、授权套餐和登录会话管理。
- 设备配对和 Runner 身份认证。
- 手机与本机 Runner 之间的 WebSocket 消息中转。
- 离线任务排队、事件索引和通知发送。
- 支付回调、授权状态和插件版本清单。
- Team Profile 同步、模板目录、匿名埋点接收、聚合指标、榜单和推荐结果。
- 安全审计、限流和异常封禁。

建议技术栈：

- `FastAPI`
- `PostgreSQL`
- `Nginx`
- `Docker Compose`
- Redis 在 Phase 2 并发或队列规模增大后引入，初始部署暂不强制。

### 5.3 本地 Agent Hub（Phase 1）

职责：

- 自动发现本机 Agent、版本和登录状态。
- 保存 Agent 实例、能力标签、用户角色配置、项目覆盖和备用链。
- 根据角色、能力、在线状态、权限和用户策略解析实际执行 Agent。
- 维护 Agent 会话、任务和子任务映射。
- 将不同 Agent 的输出统一转换为标准事件。
- 管理项目目录、worktree、进程、超时、重试和取消。
- 执行权限审批和路径越界检查。
- 作为桌面端唯一公共本地 API：只监听 `127.0.0.1` 随机端口，HTTP 使用 Bearer Token，WebSocket 使用 Bearer 换取的一次性短效 Ticket，并校验 Origin/CORS。
- 代理 Update Agent 的私有本地接口，Vue 不保存 Update Agent 端口或凭据，也不配置第二个 Base URL。
- 在断线期间继续本地任务，重连后补传事件。
- 在用户明确同意后生成最小化匿名统计事件；上传前完成字段白名单过滤和敏感信息检查。

建议实现：Python 后台服务，打包为独立可执行程序并以当前用户身份常驻。首发不注册为 `LocalSystem` 服务，因为它需要读取当前用户的 Agent 登录状态、环境变量、Git/SSH 凭据和桌面会话。数据默认保存到：

```text
%LOCALAPPDATA%\HQAgent-Hub\data\hub.db
%LOCALAPPDATA%\HQAgent-Hub\logs\
%LOCALAPPDATA%\HQAgent-Hub\worktrees\
%LOCALAPPDATA%\HQAgent-Hub\config\
%LOCALAPPDATA%\HQAgent-Hub\runtime\hub.json
```

`runtime\hub.json` 必须原子写入并设置为仅当前用户可读，至少包含 `instanceId`、`pid`、`startedAt`、随机端口和协议版本；启动 Token 不进入普通日志。

### 5.4 桌面端与升级进程

桌面端主选：`Tauri 2 + Vue 3 + TypeScript`。Tauri/Rust 只负责窗口、托盘、单实例、安全存储、开机启动和进程生命周期；业务编排留在 Local Hub。

前端作为独立工作包实施，通过手写 `UiGateway` 隔离页面与 Local Hub，提供 `MockGateway` 和 `LocalHubGateway` 两套实现。自动生成仅覆盖 OpenAPI/JSON Schema 的边界 DTO/API 类型，ViewModel 与页面 Gateway 不生成。主题从第一期开始支持 `system/light/dark`、多 Palette、密度、对比度、字号和减少动效，完整设计与验收依据见：

```text
docs/前端开发与验收方案.md
```

进程边界：

```text
hqagent-desktop.exe       Tauri/Vue UI
hqagent-core.exe          Python Local Hub
hqagent-update-agent.exe  Go OTA 状态、下载和验签
hqagent-updater.exe       Go 独立安装与回滚 Helper
Agent Worker              Claude/Codex/Gemini 等进程
```

OTA 直接复用现有 `E:\OtherPro\OTA-Platform`。更新核心提取到独立版本化模块 `E:\OtherPro\HQUpdateKit`，HQDroidDeck-Desktop 与 HQAgent-Hub 都必须改为依赖该模块；HQAgent 仅保留产品级 Update Agent/Updater 薄封装，不能复制维护第二套核心。完整设计见：

```text
docs/OTA升级架构设计.md
```

### 5.5 项目共享记忆

每个接入项目建议创建：

```text
.hqagent/
├── PROJECT_CONTEXT.md
├── ARCHITECTURE.md
├── DECISIONS.md
├── INTERFACES.md
├── tasks/
```

## 6. 动态角色、能力与团队配置

### 6.1 四层解耦模型

```text
Workflow Task
    ↓ 引用抽象角色
Role
    ↓ 声明所需能力和权限
Capability
    ↓ 由 Role Resolver 动态选择
Agent Instance
    ↓ 通过统一协议执行
Agent Adapter
```

供应商名称只用于标识 Adapter 和 Agent 实例，不能代表固定职责。工作流必须使用 `dispatch(role="architect")`，不得直接使用 `callClaude()`、`callCodex()` 等硬编码调用。

首批内置角色：

| 角色 ID | 主要职责 |
| --- | --- |
| `orchestrator` | 总控、拆解、调度、状态汇总和异常处理 |
| `architect` | 需求分析、方案、架构、接口和约束定义 |
| `frontend_implementer` | 页面、组件、样式、交互和前端测试 |
| `general_implementer` | 后端、客户端、脚本、数据库和通用工程实现 |
| `reviewer` | 方案审核、代码审查、风险检查和验收 |
| `tester` | 测试设计、执行、证据收集和回归验证 |
| `deployer` | 构建、发布、部署、回滚和运行维护 |
| `integrator` | 跨分支检查和最终合并 |

允许用户新增自定义角色。一个 Agent 可以承担多个角色，一个角色可以配置 `primary`、多个 `fallback` 和能力约束。

### 6.2 Agent 实例与能力声明

```json
{
  "agent_instance_id": "local.codex.default",
  "adapter_id": "codex",
  "display_name": "我的 Codex",
  "version": "0.147.0",
  "status": "ready",
  "capabilities": [
    "orchestration",
    "architecture",
    "coding",
    "review",
    "testing",
    "shell",
    "session_resume",
    "structured_output"
  ]
}
```

能力由 Adapter 提供默认检测结果，用户可以补充偏好，但不能手动绕过 Adapter 明确不支持的硬能力。

### 6.3 Team Profile

当前用户的配置示例：

```yaml
profile_name: HQ默认团队
roles:
  orchestrator: { primary: claude.default }
  architect: { primary: claude.default }
  reviewer: { primary: claude.default }
  frontend_implementer: { primary: gemini.antigravity }
  general_implementer: { primary: codex.main }
  tester:
    primary: codex.main
    fallback: [claude.default]
```

只有 Codex 和 DeepSeek 的用户可以配置：

```yaml
profile_name: Codex-DeepSeek团队
roles:
  orchestrator: { primary: codex.main }
  architect: { primary: codex.main }
  reviewer:
    primary: codex.main
    fallback: [deepseek.local]
  frontend_implementer:
    primary: deepseek.local
    fallback: [codex.main]
  general_implementer: { primary: deepseek.local }
  tester: { primary: codex.main }
```

配置层级：

```text
单次任务覆盖
    ↓
项目 Team Profile
    ↓
用户全局 Team Profile
    ↓
能力自动匹配
    ↓
备用 Agent
    ↓
提示用户选择或暂停节点
```

### 6.4 路由与降级策略

```yaml
policies:
  missing_agent_strategy: fallback_then_ask
  allow_one_agent_multiple_roles: true
  prefer_cross_agent_review: true
  same_agent_review_strategy: isolated_session
```

- 首选 Agent 不在线时，按备用链和能力匹配选择替代实例。
- 只有一个 Agent 时，允许它承担全部角色。
- 实现和审核由同一个 Agent 承担时，审核必须使用独立 Session，并重新读取验收标准和 Diff。
- 路由结果必须记录选择来源：单次指定、项目配置、全局配置、自动匹配或故障降级。
- 如果缺少视觉、浏览器、Shell、会话恢复等硬能力，必须提示能力缺口，不得伪装成正常完成。

### 6.5 角色权限

权限和可写路径绑定角色，不绑定 Agent 品牌：

```yaml
role_permissions:
  architect:
    filesystem: read_only
    shell: false
  frontend_implementer:
    writable_paths: ["frontend/**", "web/**", "ui/**"]
  reviewer:
    filesystem: read_only
    can_approve: true
  general_implementer:
    writable_paths: ["backend/**", "server/**", "app/**"]
```

替换 Agent 后仍沿用同一角色权限，避免因为更换供应商而扩大本机访问范围。

### 6.6 通用执行流程

```text
用户选择场景和 Team Profile 后提交目标
→ Orchestrator Runtime 把工作流节点分派给角色
→ Role Resolver 根据配置、能力、状态和策略解析 Agent 实例
→ 各 Agent 读取项目共享记忆和任务契约
→ Worker 在独立 worktree 执行并回传结构化结果
→ reviewer/tester 角色执行独立复核
→ integrator 或人工审批完成合并
→ Phase 1 桌面端收到结果、实际角色分工和验证证据；Phase 2 再同步到手机端
```

### 6.7 冲突控制

- W0 必须先初始化 Git、提交基线并建立 `integration/phase1`；每个并行工作包从同一固定 `baseCommit` 创建独立物理 worktree，不能只开多个终端共用一个目录。
- 每个写任务默认使用独立 Git worktree 和分支。
- 任务包含允许修改的路径列表。
- 执行完成后通过 `git diff --name-only` 校验职责边界。
- 跨端接口先由 `architect` 更新 `INTERFACES.md`，执行角色按契约实现。
- 默认只允许一个 `integrator` 执行最终合并。

## 7. 通用 Agent Adapter 协议

### 7.1 适配方式

按可靠性优先级支持：

1. 官方 SDK/App Server。
2. CLI JSON/JSONL/stream-json。
3. MCP 或 A2A 远程 Agent。
4. 桌面 Sidecar/插件接口。
5. GUI 屏幕自动化仅作为实验性兜底，不作为正式适配器标准。

### 7.2 核心接口

```typescript
interface AgentAdapter {
  detect(): Promise<AgentInfo>;
  health(): Promise<AgentHealth>;
  start(task: AgentTask): Promise<AgentSession>;
  resume(sessionId: string, message: string): Promise<void>;
  streamEvents(sessionId: string): AsyncIterable<AgentEvent>;
  approve(requestId: string, decision: ApprovalDecision): Promise<void>;
  cancel(sessionId: string): Promise<void>;
  collectResult(sessionId: string): Promise<AgentResult>;
}
```

### 7.3 能力声明

适配器必须声明：

- 是否支持会话恢复。
- 是否支持流式事件。
- 是否支持工具审批。
- 是否支持结构化结果。
- 是否支持文件修改。
- 是否支持 Git/worktree。
- 所需鉴权类型：本地登录、API Key、OAuth、设备码等。
- 支持的平台和最低版本。

### 7.4 分阶段适配器

- Phase 1 Claude：Claude Agent SDK 或本机 Claude Code 进程，保存 `session_id`。
- Phase 1 Codex：Codex SDK/App Server，保存 `thread_id`。
- Phase 1.1 Antigravity：Sidecar + `agentapi` 创建/续接会话，保存 `conversation_id`；通过共享 MCP 工具回报进度和结果。
- Phase 1.1 Gemini CLI：使用 headless JSONL 和显式 session ID 续接。

### 8.1 任务结构

```json
{
  "task_id": "TASK-20260905-001",
  "node_id": "node-frontend-001",
  "project_id": "project-001",
  "parent_task_id": null,
  "team_profile_id": "profile-hq-default",
  "target_role": "frontend_implementer",
  "agent_override": null,
  "session_purpose": "implementation",
  "resume_session_id": null,
  "objective": "实现设备批量导入",
  "allowed_paths": ["apps/desktop/**"],
  "read_first": [
    ".hqagent/ARCHITECTURE.md",
    ".hqagent/INTERFACES.md"
  ],
  "acceptance": ["pnpm test", "pnpm build"],
  "requires_approval": ["deploy", "git_push", "delete"]
}
```

### 8.2 会话注册

```text
local_session_id
  → user_id / device_id / project_id
  → task_id / node_id / purpose / parent_session_id
  → role_id / agent_instance_id / external_session_id / reuse_policy
```

示例：

```text
session-001 / task-001 / node-plan / architecture / claude.default → claude-session-aaa
session-002 / task-001 / node-code / implementation / codex.main   → codex-thread-bbb
session-003 / task-002 / node-code / implementation / codex.main   → codex-thread-ccc
```

`task-001` 与 `task-002` 即使项目、角色和 Agent 完全相同，也必须创建不同的本地 Session 和外部 Session，避免无关任务串线。只有用户明确点击“继续会话”、工作流显式声明复用，或任务传入 `resume_session_id` 时，才恢复指定会话；项目背景通过 `.hqagent` 共享记忆和 Handoff 注入，不靠把所有工作塞进一个长期对话。

禁止使用不确定的 `latest` 作为默认续接方式；必须保存并传递明确的本地 Session ID 和供应商外部会话 ID。审核与实现由同一 Agent 承担时，审核使用 `purpose=review` 的隔离 Session。

## 9. 数据埋点、榜单与模板推荐体系

### 9.1 产品目标

埋点体系用于回答以下产品问题：

- 用户通常把哪个 Agent 设置为 `orchestrator`、`architect`、`reviewer`、`frontend_implementer` 等角色。
- 不同场景下最常见的 Team Profile 和 Agent 组合是什么。
- 哪些模板被查看、采用、保留、修改或放弃。
- 某种角色分配在特定场景下的完成率、返工率、耗时区间、稳定性和用户满意度如何。
- 当前用户安装的 Agent 组合适合套用哪些官方或社区模板。

数据闭环：

```text
用户配置团队
→ 匿名记录角色分配和使用结果
→ 云端按场景聚合
→ 生成热门榜单与效果指标
→ 形成可复用 Team Profile 模板
→ 按用户已安装 Agent 和偏好推荐
→ 用户采用、修改和评价
→ 持续优化模板
```

### 9.2 数据分级与边界

| 数据级别 | 示例 | 处理原则 |
| --- | --- | --- |
| 服务必要数据 | 账号、设备、授权、任务状态、支付结果 | 仅用于提供云服务，不能混同为产品分析同意 |
| 本地个性化数据 | 完整 Team Profile、项目偏好、Agent 实例状态 | 默认保存在本机，可选择加密同步 |
| 可选匿名分析数据 | 角色对应的 Agent 家族、场景、模板、路由来源、结果指标 | 用户明确同意后上传，只使用字段白名单 |
| 禁止进入分析系统 | 提示词、代码、项目名称和路径、文件名、命令输出、Diff、密钥、会话 ID、Agent 实例昵称 | Local Hub 上传前剔除，云端再次校验拒收 |

任务事件流和分析埋点必须是两个独立通道。不能直接把 `agent.progress`、日志或结果正文复制到统计系统。

### 9.3 统一埋点事件

```json
{
  "event_id": "aevt-001",
  "event_name": "role_binding.changed",
  "schema_version": 1,
  "occurred_at": "2026-09-05T18:00:00+08:00",
  "analytics_id": "rotating-anonymous-id",
  "hub_version": "0.1.0",
  "platform": "windows",
  "properties": {
    "role_id": "architect",
    "agent_family": "codex",
    "scenario_id": "web_application",
    "binding_scope": "project",
    "source": "manual"
  }
}
```

首批事件字典：

| 事件 | 触发时机 | 关键统计字段 |
| --- | --- | --- |
| `team_profile.created` | 创建团队配置 | 角色数量、Agent 家族数量、来源 |
| `team_profile.activated` | 启用团队配置 | 场景、模板 ID、是否修改模板 |
| `role_binding.changed` | 调整角色分配 | 角色、Agent 家族、配置层级、来源 |
| `task.routed` | Role Resolver 完成选择 | 角色、Agent 家族、路由来源、是否降级 |
| `task.completed` | 任务结束 | 场景、角色、Agent 家族、结果、耗时区间、重试次数 |
| `template.viewed` | 查看模板 | 模板、场景、推荐位置 |
| `template.applied` | 套用模板 | 模板、可满足角色数、替换数量 |
| `template.retained` | 使用一段时间后仍保留 | 模板、修改程度、使用任务数区间 |
| `template.rated` | 用户主动评价 | 评分、是否推荐、可选原因标签 |
| `recommendation.adopted` | 采用推荐结果 | 推荐策略、排名位置、是否再次修改 |

`task.completed` 只记录结构化枚举和数值区间，不记录任务目标、总结、错误正文或测试输出。

### 9.4 核心指标与榜单

首批可以形成：

- 角色热度榜：每个角色被分配给 Claude、Codex、Gemini、DeepSeek、GLM 等 Agent 家族的占比。
- 团队组合榜：按场景统计最常见的角色-Agent 组合，例如“Claude 指挥 + Gemini 前端 + Codex 通用实现”。
- 模板采用榜：查看量、采用率、7/30 天保留率和用户评分。
- 场景适配榜：Web 应用、后端 API、Android、DevOps、代码审核、缺陷修复等场景的常用组合。
- 路由稳定性：首选命中率、备用 Agent 使用率、能力缺失率和会话恢复成功率。
- 效果指标：任务完成率、失败率、返工次数区间、耗时区间和用户主动评分。

“最热门”和“效果最好”必须分开展示。市场占有率高不代表某 Agent 在该角色上效果最好，榜单必须同时展示样本量、统计周期、Hub/Agent 版本范围和置信度。

公开榜单建议至少满足：

```text
独立匿名用户数 >= 20
有效完成任务数 >= 100
统计周期 >= 7天
```

不足阈值时只显示“样本不足”，不生成误导性排名。

### 9.5 场景模板与动态适配

模板不能只保存固定供应商组合，还要保存角色所需能力，使模板可以适配不同用户的本机 Agent：

```json
{
  "template_id": "web-team-balanced-v1",
  "name": "Web应用三角色均衡团队",
  "scenario_id": "web_application",
  "roles": [
    {
      "role_id": "architect",
      "required_capabilities": ["architecture", "review"],
      "preferred_agent_families": ["claude", "codex"]
    },
    {
      "role_id": "frontend_implementer",
      "required_capabilities": ["coding"],
      "preferred_capabilities": ["vision", "browser"]
    },
    {
      "role_id": "general_implementer",
      "required_capabilities": ["coding", "shell", "testing"]
    }
  ],
  "policies": {
    "prefer_cross_agent_review": true,
    "missing_agent_strategy": "fallback_then_ask"
  }
}
```

推荐服务先筛选用户本机能够满足的角色和能力，再参考场景、用户偏好、热门度和效果指标排序。推荐结果必须说明原因，例如“你已安装 Codex 和 DeepSeek；该模板可覆盖全部角色，其中 Codex 更常被用于架构和审核”。

### 9.6 隐私、偏差与防刷

- 首次启用匿名产品分析时单独征得同意，允许随时关闭、查看待上传字段和申请删除云端匿名数据。
- 使用可轮换的 `analytics_id`，不上传本机用户名、设备名、Agent 实例昵称和第三方账号标识。
- 建议原始匿名事件保留 30 天，按日聚合数据保留周期在正式运营前依据地区法规确认。
- 榜单按用户去重并限制单设备/单账号贡献权重，防止高频任务刷榜。
- Agent 大版本、适配器版本和模板版本发生变化时分段统计，避免历史结果掩盖当前表现。
- 不向第三方出售用户级埋点数据；商业化面向模板、推荐和协作服务，不出售用户画像。
- 用户未同意云端统计时，仍可使用本地 Team Profile、本地历史统计和官方静态模板。

### 9.7 存储与服务边界

Phase 1 只在本地 SQLite 保存 Team Profile、任务、Session 和可选的本地分析预览，不建设云端统计库。Phase 2 的 Control Plane 使用 PostgreSQL，优先建立以下逻辑表：

```text
team_profile_catalog
template_versions
telemetry_events_raw
role_agent_metrics_daily
team_combination_metrics_daily
template_metrics_daily
recommendation_feedback
```

原始事件与账号业务库逻辑隔离，公开榜单只读取聚合表。数据量明显增长后再考虑 ClickHouse 等分析存储，不在 Phase 2 初期过早引入。

## 10. 接口与事实源边界

### 10.1 Local Hub 公共 API（Phase 1）

`packages/protocol/openapi/local-hub.v1.yaml` 是桌面端唯一网络契约。Vue/Tauri 只配置 Local Hub 一个 Base URL；HTTP 请求使用 `Authorization: Bearer <startup-token>`，原生 WebSocket 不能依赖自定义 Header，必须先调用 `POST /api/v1/auth/ws-ticket` 换取 30 秒有效、单次使用的 Ticket。

Local Hub 提供 bootstrap、Agents、Team Profiles、Tasks、Sessions、Approvals、Settings、事件恢复和 `docs/OTA升级架构设计.md` §13.2 的 9 条更新路径。Update Agent 仅实现 `packages/protocol/openapi/update-agent.internal.v1.yaml` 定义的私有本地 API，由 Local Hub 代理；Vue 不得读取其端口或凭据。事件先持久化再发送，Local Hub 统一分配单调 `seq`；游标过期返回 `EVENT_CURSOR_EXPIRED` 和 Snapshot 恢复信息。

### 10.2 云端 API 初步约定（Phase 2）

```text
POST /api/v1/auth/login
POST /api/v1/devices/pair
GET  /api/v1/devices
POST /api/v1/tasks
GET  /api/v1/tasks/{task_id}
POST /api/v1/tasks/{task_id}/messages
POST /api/v1/tasks/{task_id}/cancel
POST /api/v1/approvals/{approval_id}
GET  /api/v1/projects
GET  /api/v1/team-profiles
PUT  /api/v1/team-profiles/{profile_id}
GET  /api/v1/templates
GET  /api/v1/templates/recommended
POST /api/v1/templates/{template_id}/feedback
GET  /api/v1/insights/role-agents
GET  /api/v1/insights/team-combinations
POST /api/v1/telemetry/events:batch
WS   /ws/v1/app
WS   /ws/v1/runner
```

所有写请求必须具有请求 ID 或幂等键，防止手机重试和网络重连导致重复执行。

### 10.3 OTA Platform 公开接口

OTA Platform 保持独立服务边界，复用：

```text
GET /api/v1/updates/check
GET /api/v1/updates/releases
GET /packages/{path}
```

HQAgent Cloud 可以在 Phase 2 同步升级提示和远程审批，但不能取代本机 Update Agent 完成验签、任务排空和安装。远端版本/渠道/制品以 OTA Platform 为事实源，本机升级状态以 Update Agent 为事实源，桌面展示与事件入口以 Local Hub 为事实源。

## 11. 远程连接与 FRP 边界

### 11.1 商业版推荐

本地 Agent Hub 主动连接 VPS：

```text
Local Hub → wss://agent.example.com/ws/v1/runner
```

优点：

- 用户不需要公网 IP。
- 用户不需要配置路由器、端口或 FRP。
- 网络中断后可以自动重连。
- 云端可以在设备离线时保存任务。
- 公网不直接暴露用户电脑上的 Agent 服务。

### 11.2 自用/原型 FRP

现有 FRP 可以用于早期验证，但只能把本地控制服务映射到 VPS 内网监听端口，再由 Nginx 提供 HTTPS；禁止直接把 Claude、Codex、Antigravity 原始端口映射到公网。

## 12. 安全设计

### 12.1 账号与设备

- 手机登录使用短期 Access Token 和可撤销 Refresh Token。
- 设备通过二维码或一次性验证码配对。
- Runner 使用独立设备密钥和签名挑战认证。
- 支持设备远程注销、密钥轮换和异常登录提醒。

### 12.2 Agent 与凭据

- 各 Agent 的登录信息和 API Key 默认只保存在用户电脑。
- 云端不接收或保存用户的 Claude、OpenAI、Google 等供应商凭据。
- 商业模式采用 BYOA/BYOK，不共享、不代理、不转售用户订阅。
- 各供应商适配器必须遵循对应鉴权和商业使用条款。

### 12.3 远程执行

- 项目必须显式授权目录范围。
- Agent 默认最小权限运行。
- 删除、部署、数据库迁移、生产环境操作、`git push` 等需要远程审批。
- 禁止默认开启 `dangerously-skip-permissions`、`yolo` 或同类全部放行模式。
- 所有任务、审批、命令和结果保留审计事件。

### 12.4 数据保护

- 公网通信全部使用 TLS。
- P1 引入手机与本机 Runner 之间的端到端加密，VPS 只中转密文。
- 推送通知不包含源代码、密钥和完整命令输出。
- 大文件和构建产物默认留在本机；如需云端分享，使用独立对象存储和短期签名 URL。

### 12.5 埋点隐私控制

- 服务必要数据、审计日志和可选产品分析采用不同用途声明、表结构和保留策略。
- Local Hub 只允许上传已登记的埋点事件和字段；任何额外字段默认拒绝。
- 设置页提供“查看将上传的数据”“停止匿名统计”“重置匿名标识”和“申请删除”入口。
- Team Profile 云端同步与匿名榜单统计分别授权，不能通过开启同步默认获得统计同意。
- 开发和测试环境使用独立数据集，禁止把真实用户事件复制到非生产环境。

## 13. 安装与用户体验

### 13.1 完整商业用户目标流程

1. 下载并安装 `HQAgent-Hub`。
2. 当前用户级 NSIS 安装程序将应用安装到 `%LOCALAPPDATA%\Programs\HQAgent-Hub`，注册托盘自启动并拉起 Local Hub。
3. 软件启动后检查自身组件完整性和 OTA 更新状态，再自动检测本机 Agent、版本和登录状态。
4. “组建 AI 团队”向导让用户为各角色选择 Agent，也可以套用单 Agent、双 Agent 或三 Agent 模板。
5. 用户选择允许访问的项目目录，并按项目覆盖团队角色和可写范围。
6. 用户独立选择是否参加匿名产品分析，并可预览收集字段。
7. Phase 2 手机扫描二维码绑定设备。
8. Phase 2 开始发送远程任务；Phase 1 在桌面端直接发送本地任务。

普通用户不应手工配置：

- FRP
- Nginx
- MCP JSON
- WebSocket 地址
- Windows Task Scheduler
- Agent 会话 ID
- 数据库

### 13.2 安装包职责

- P0 固定使用 `windows-nsis + current-user`，程序目录为 `%LOCALAPPDATA%\Programs\HQAgent-Hub`，数据目录为 `%LOCALAPPDATA%\HQAgent-Hub`，默认不要求管理员权限；系统级安装、MSI 和 Portable 不进入一期验收。
- 自动安装/升级当前用户 Local Hub 后台进程、桌面壳和内置 Adapter。
- 安装 `HQAgentUpdateAgent` 和独立 `HQAgentUpdater`，注册 stable/beta 更新配置。
- 升级前停止新任务，等待 Desktop、Local Hub、Update Agent 和全部 Agent Worker 排空，保存任务 checkpoint、Session Registry、配置；执行 WAL checkpoint 后使用 SQLite Backup API 生成一致性数据库快照。有活动任务时不得静默覆盖安装。
- 升级包必须通过大小、SHA-256、Ed25519 和平台 Target 校验；Windows/macOS 正式发行还需要操作系统代码签名。
- 新版本启动后必须执行进程、HTTP 和协议健康检查；失败时自动恢复上一版本程序/安装器和升级前数据库快照，健康检查通过前持续保持维护模式。
- 更新核心来自双方产品共同依赖的版本化 `HQUpdateKit`，HQAgent-Hub 只维护产品配置和薄封装。
- 自动发现 Agent 和执行文件路径。
- 提供 Agent 能力检测、角色拖拽分配、备用链配置和 Team Profile 导入导出。
- 对缺失 Agent 给出安装指引，不默认静默安装第三方软件。
- 自动写入必要的插件、MCP 或 Sidecar 配置，并提供可回滚备份。
- 提供诊断页面：网络、权限、Agent 登录、能力、角色覆盖、版本、项目目录和服务状态。
- 提供隐私中心和本地埋点队列查看器。

## 14. VPS 部署方案

### 14.1 初期推荐配置

```text
CPU：2核
内存：4GB
磁盘：40～80GB NVMe
带宽：10Mbps或以上
系统：Debian 12 / Ubuntu 24.04
```

VPS 不运行用户代码和 Agent 构建任务，因此早期主要压力来自 WebSocket 连接、数据库、日志、TLS、消息中转和小规模聚合统计。内测阶段埋点按批上传并按日聚合，`2核4GB` 仍可满足早期使用。

### 14.2 服务组成

```text
Nginx
HQAgent API
HQAgent Web/PWA
PostgreSQL
后台任务进程
备份任务
可选：Redis
复用现有独立 OTA Platform（可同机不同服务/域名）
```

### 14.3 网络边界

- 公网只开放 `80/443`，HTTP 自动跳转 HTTPS。
- SSH 优先密钥登录并限制来源。
- PostgreSQL、Redis 和内部 API 不直接暴露公网。
- Nginx 负责 TLS、限流和 WebSocket 反向代理。
- 主机防火墙只负责源站端口控制；公网攻击和流量成本需要云厂商安全组、CDN/WAF 或上游防护共同处理。

### 14.4 日志与备份

- API、Nginx、支付、授权和异常日志分开保存。
- 日志设定滚动和保留期限，禁止记录凭据与完整源代码。
- PostgreSQL 每日备份，并验证恢复流程。
- 版本升级前保留数据库和配置回滚点。

## 15. 商业闭环

### 15.1 收费对象

收费内容是：

- 手机远程控制。
- 多设备授权。
- 任务中转和离线队列。
- 推送通知。
- 多 Agent 编排、会话管理和任务恢复。
- 定时任务、工作流模板、热门榜单、场景推荐和长期历史。
- 团队权限、审计和私有部署。

不收费或不代理的内容：

- 第三方模型额度。
- 用户的 Claude、OpenAI、Google 等账号。
- 用户自己的 API 消耗。

### 15.2 套餐建议

| 套餐 | 建议价格 | 主要能力 |
| --- | ---: | --- |
| Free | 免费 | 本地控制、单设备、无持续云服务 |
| Pro | ¥99/年 | 手机远程、3台设备、任务历史、通知、公共模板 |
| Pro+ | ¥199～299/年 | 多 Agent 编排、定时任务、个性化推荐、更多设备和历史 |
| Team | ¥599/年起 | 团队成员、角色权限、审计、私有指标和共享模板 |
| Local Lifetime | ¥99～199一次性 | 本地永久功能，不承诺持续云资源 |

不建议使用“¥99 一次买断永久云服务”，可以将其作为限量早鸟权益，但需要限制设备、历史、存储或持续服务范围。

### 15.3 授权机制

- 支付成功后云端生成 Entitlement。
- 账号、套餐、设备数量和有效期由云端控制。
- Local Hub 缓存短期签名授权，允许有限时间的离线宽限。
- 云端远程功能必须依赖有效订阅，本地免费功能不应因云服务故障完全不可用。
- 榜单基础数据可作为公共产品能力；高级场景推荐、团队私有模板和私有效果指标可以进入 Pro+/Team 套餐。
- 不以出售用户级埋点或第三方广告画像作为商业模式。

## 17. Phase 1 验收标准

本节给出产品级出口；逐工作包、冻结点和集成剧本以 `docs/分工与并行开工方案.md` §5、§7、§10、§11 为执行清单。

1. Git 基线、`integration/phase1` 与各并行工作包的独立物理 worktree 已建立，每个任务记录 `baseCommit`、分支、路径和 `allowedPaths`。
2. Windows 当前用户可以安装并启动桌面端；程序与数据目录分离，默认不要求 UAC。
3. 桌面端只连接 Local Hub 一个 Base URL，真实展示 Claude/Codex 的版本、登录状态和能力清单。
4. 用户可以创建、切换和导入 Team Profile；同一工作流在 Claude/Codex 角色互换后不修改业务代码仍可运行。
5. `architect` 产出任务契约和可验证验收条件，`general_implementer` 在独立 worktree 执行，`reviewer` 基于真实 Diff、命令输出和测试证据审核。
6. 两个无关任务即使项目、角色和 Agent 相同，也使用不同本地/外部 Session；显式 `resume_session_id` 可以准确恢复指定会话。
7. Local Hub 重启后能够恢复任务、Session、Team Profile、审批状态和事件游标；游标过期可按 Snapshot 恢复。
8. 首选 Agent 离线时命中备用 Agent，并展示 `resolve_source`/降级原因；硬能力缺失时暂停或提示，不能伪装完成。
9. 写任务越界修改会被 `git diff --name-only` 检出并拦截，现场保留供审查。
10. 危险操作在桌面端进入审批；拒绝后节点进入明确的取消、阻塞或重规划状态，未经批准不执行。
11. `system/light/dark`、至少两套 Palette、密度/字号/减少动效设置工作正常，页面覆盖 loading/empty/error/offline 状态。
12. HTTP 无 Bearer 返回 401；Bearer 可换一次性 WS Ticket，Ticket 重放和非法 Origin 被拒，敏感 Token/Ticket 不进入日志。
13. 协议 DTO 由统一 Schema/OpenAPI 生成且生成命令幂等；手写 `UiGateway`/ViewModel 不与生成层互相污染，原子契约 Fixture 与 UI 场景 Fixture 分层。
14. OTA Platform 可按 `hqagent-hub + targetKey + channel` 返回正确制品，产品版本、协议版本和数据库版本相互独立。
15. 下载取消/续传可恢复；篡改包、错误签名、错误 OS/arch/安装类型均不能进入安装状态。
16. 有运行任务时升级先停止新任务、checkpoint、WAL checkpoint/SQLite Backup，并等待 Desktop、Local Hub、Update Agent 和全部 Worker 退出后才安装。
17. 当前用户级 NSIS 可以完成真实升级、重启和一次性结果回执；新版本健康检查失败时自动恢复上一版本程序及数据库快照，任务、Session、Team Profile 和配置不丢失。
18. HQDroidDeck-Desktop 与 HQAgent-Hub 的更新核心来自同一版本化 `HQUpdateKit`，不存在复制维护的第二套核心。

## 18. 主要风险与应对

| 风险 | 影响 | 应对措施 |
| --- | --- | --- |
| Agent CLI/SDK 频繁升级 | 适配器失效 | 能力探测、版本范围、兼容测试、独立适配器发布 |
| 会话过长或上下文压缩 | 质量下降 | 共享记忆、阶段性 handoff、新会话可恢复引导 |
| 多 Agent 文件冲突 | 代码覆盖、合并失败 | 独立 worktree、路径所有权、单一 Integrator |
| 远程命令权限过大 | 数据或系统风险 | 最小权限、审批门禁、路径限制、审计和沙箱 |
| 用户网络/电脑离线 | 任务中断 | 云端队列、本地持久化、心跳、断线重连和幂等 |
| 第三方账号和商业条款 | 无法公开销售 | BYOA/BYOK，不转售额度，逐供应商审核接入方式 |
| VPS 被攻击或流量异常 | 服务中断和费用风险 | 安全组、WAF/CDN、限流、密钥轮换、监控和备份 |
| 安装配置过于复杂 | 用户流失 | 单一安装包、自动检测、二维码配对、内置诊断 |
| ¥99 定价覆盖不了支持成本 | 商业不可持续 | 年付订阅、功能分层、支持范围和资源配额 |
| 埋点意外收集代码或任务内容 | 隐私与信任风险 | 独立统计通道、字段白名单、本地过滤、云端拒收和自动化测试 |
| 热门度被误解为能力排名 | 推荐误导用户 | 热门与效果分榜、展示样本量/版本/周期、使用置信度和平滑算法 |
| 早期样本过少 | 榜单波动且无参考价值 | 最小展示阈值、只发布趋势、不足样本不排名 |
| 单用户或自动任务刷榜 | 指标失真 | 按匿名用户去重、贡献上限、异常检测和聚合延迟 |
| Agent/模型升级造成历史指标失真 | 旧结论误导当前选择 | 按大版本和统计窗口分段，模板指标带版本范围 |
| 更新时终止正在工作的 Agent | 未提交代码、会话或任务状态丢失 | 维护模式、停止新任务、checkpoint、超时审批和任务排空 |
| 更新包或 Manifest 被篡改 | 客户端供应链风险 | HTTPS、大小、SHA-256、Ed25519、独立产品密钥和 OS 代码签名 |
| 新版本无法启动或数据库不兼容 | 大量客户端不可用 | 安装前备份、Schema 版本、启动健康检查、自动本机回滚和渠道暂停 |
| OTA Platform 当前无百分比灰度 | 问题版本影响面过大 | 先使用 beta/stable，P1 增加稳定分桶、暂停发布和分阶段放量 |
| 更新核心在两个产品中再次分叉 | 安全修复不同步 | 建立独立版本化 `HQUpdateKit`，HQDroidDeck-Desktop 与 HQAgent-Hub 共同依赖并执行兼容性测试 |
