# 桌面壳框架选型对比：Tauri/Rust vs Wails/Go

| 版本 | 日期 | 变更 |
| --- | --- | --- |
| v0.1 | 2026-09-06 | 依据既有五份文档与 HQDroidDeck-Desktop 实况，重新论证 W5 桌面壳框架选型 |
| v0.2 | 2026-09-06 | 用户裁决手机端排除出选型考量，技术栈开放；补记协议包需新增 Dart/Kotlin 目标 |

## 0. 为什么现在写这份

W5 桌面壳在原始文档里是**无主状态**（见 `分工与并行开工方案.md` §52：前端文档 §1 明确不实现 Agent 进程控制，施工方案 §5.4 只给了粗粒度职责）。Tauri 是从既有文档继承下来的既定条件，`.hqagent/DECISIONS.md` 里 D11–D16 全是协议层决策，**没有任何一条论证过桌面框架**。

现在被 MSVC 工具链缺失卡住，正好是把这个前提补论证的时机。

## 1. 先纠正我上一轮的两个错误说法

### 错误一：「Go 壳可以直接 import HQUpdateKit，不用隔一个私有 HTTP API」

**错的。** `OTA升级架构设计.md` §4.2 定死了五进程边界：

```text
hqagent-desktop.exe       桌面壳和托盘
hqagent-core.exe          Local Hub
hqagent-update-agent.exe  更新状态、下载和验签
hqagent-updater.exe       主程序退出后执行替换/安装
agent worker processes    Claude/Codex/Gemini 等进程
```

Update Agent 独立是因为「更新时桌面窗口关闭不代表升级状态丢失」，Updater 独立是因为它必须在主程序被替换时还活着。**这是架构约束，不是语言约束。** 壳换成 Go，这两个仍然是独立 Go 二进制，私有接口一条也少不了。HQUpdateKit 的复用度与壳用什么语言**完全无关**。

### 错误二：「倾向 Go，因为跨平台更省事」

**方向错了。** 见下面第 3 节：Go 免工具链这件事**只在 Windows 成立**，到 macOS/Linux 就没了。

## 2. 手机端：已由用户明确排除出选型考量

**2026-09-06 用户裁决：手机端不参与桌面壳选型判断，技术栈开放（PWA / 原生 Android / Flutter 均可）。**

这与查阅资料得出的结论一致，且更彻底。原文档的表述是：

| 出处 | 原文 |
| --- | --- |
| `施工方案.md` §53 | Phase 2 的手机端**优先采用 Vue 3 PWA**，后续按需要使用 Capacitor 打包 Android/iOS 应用 |
| `前端开发与验收方案.md` §108 | 第一期桌面端只预留展示和事件入口，完整手机端不在本工作包内 |
| `OTA升级架构设计.md` §523 | 手机端接入时**只通过云端命令转发到绑定设备**，安装动作最终必须由本地 Update Coordinator 执行 |

我全量搜过 `局域网 / LAN / 直连 / 内网穿透 / 中继`——**零命中**。手机永远走云端 Control Plane，从不直连 Local Hub。手机端是纯瘦客户端：不跑 Hub、不管进程、不读 hub.json。

**对选型的影响**：Tauri 2 最大的差异化卖点就是移动端一等公民（Wails v2/v3 都没有）。手机端排除后，**这个卖点在本项目彻底归零**。本对比的其余部分不依赖这一条，故结论不变。

### 2.1 但有一个后果落在 packages/protocol 上

手机端若走**原生 Android（Kotlin）或 Flutter（Dart）**，而不是 PWA 复用现有 TS 类型，则协议包需要新增一个语言目标。

`scripts/protocol/generate.py` 现在是 `lang: int`（0=ts / 1=py / 2=go），类型映射散布在约 8 处 `{0:..., 1:..., 2:...}[self.lang]` 字典里，加上三个 `emit_*` 函数。新增第四个目标的工作量：扩 `PRIMITIVES` 表 + 那 8 处字典 + 一个约 60–90 行的 `emit_dart` / `emit_kotlin`，量级是一天，不是架构改动。

因为 D12 定的是**自建生成器、零第三方工具链**，这件事完全在自己手里，没有外部生成器的版本漂移风险。但要记住 D12 的代价：只支持本仓库用到的 Schema 子集，不支持 `oneOf/anyOf/allOf`。

**这条属于 W0（协议包）的 Phase 2 待办，与 W5 桌面壳选型无关，不阻塞当前决策。**

## 3. 跨平台：Go 的免工具链优势只在 Windows 成立

### 3.1 跨平台在路线图的真实位置

| Phase | 内容 | 出处 |
| --- | --- | --- |
| Phase 1 / P0 | **仅 Windows**。组件和主题必须跨平台友好，但只验收 Windows | `前端开发与验收方案.md` §1285 |
| Phase 2 / P1 | 云端 Control Plane、手机 PWA、支付授权 —— **不含桌面跨平台** | `施工方案.md` §3.3 |
| Phase 3 / P2 | **macOS、Linux 支持** | `施工方案.md` §3.4 |

`OTA升级架构设计.md` §195 的制品表把 macOS 标成 P1、Linux 标成 P2，与施工方案 §3.4 的 Phase 3 略有张力，但方向一致：**macOS/Linux 在云端和手机之后**，隔着两个阶段。

`OTA升级架构设计.md` §647 还明确：「Windows 闭环稳定后再实现 macOS，不同时开工所有平台。」

### 3.2 到了 Phase 3，两边的工具链负担趋同

| 平台 | Tauri/Rust 需要 | Wails/Go 需要 |
| --- | --- | --- |
| Windows | **MSVC Build Tools（link.exe + Windows SDK）** | 无（Wails on Windows 免 cgo，走 go-winloader 动态加载 WebView2） |
| macOS | Xcode Command Line Tools | Xcode Command Line Tools（**Wails 在 macOS 需要 cgo**） |
| Linux | gcc + webkit2gtk 开发包 | gcc + webkit2gtk 开发包（**同样需要 cgo**） |

WebView 引擎两边完全一样：Windows 用 WebView2、macOS 用 WKWebView、Linux 用 WebKitGTK。

所以「Go 不用装工具链」**只是 Windows 上的一次性差异**，到 macOS/Linux 就抹平了。

> 置信度说明：Windows 侧免 cgo 这条我在本机实证了（见 §4）。macOS/Linux 侧需要 cgo 是 Wails 官方前置条件，本机无法验证，属于文献而非实测。

### 3.3 一个反直觉的推论

如果**跨平台是选型的主要驱动力**，那它其实**不构成换 Go 的理由**——因为跨平台阶段两边成本一样。
Go 的收益集中在「Phase 1 这台 Windows 机器上少装 2-3 GB」，是**当下的便利**，不是**路线的优势**。

## 4. HQDroidDeck 的可复用性：壳代码不可复用，发布链路可复用

`E:\OtherPro\HQDroidDeck-Desktop` 是同一作者的 Wails v2.12.0 + Go 1.26 桌面应用。

### 4.1 本机实证

```
build/bin/HQDroidDeck.exe        17,113,600 字节   2026-09-05 23:12
build/bin/HQDroidDeckUpdater.exe  6,622,720 字节   2026-09-05 23:12
```

**在这台没有任何 MSVC 的机器上编出来的**，全仓库 `import "C"` 零命中。Wails on Windows 免 cgo 这条到此实证。

### 4.2 壳代码是 Windows 专用的，跨平台复用价值为零

```
cmd/updater/platform_windows.go
internal/adbcore/platform_windows.go
internal/adbcore/process_windows.go
internal/logcat/process_windows.go
internal/media/clipboard_windows.go
internal/systemops/platform_windows.go
internal/update/installer_windows.go
```

**7 个 `*_windows.go`，0 个 `_darwin.go`，0 个 `_linux.go`。** HQDroidDeck 是个 ADB/安卓设备助手，Windows-only 是合理的产品选择，但也意味着：

我上一轮说的「单实例/托盘/自启/窗口状态能从 HQDroidDeck 直接抄」——**在 Windows 上成立，到 Phase 3 一行都不能用**，那些都要为 macOS/Linux 重写，跟壳用什么语言无关。

### 4.3 真正可复用的是发布链路，而这一条 Tauri 反而要付额外代价

```
scripts/build.ps1                  用 Inno Setup（ISCC.exe）打包
scripts/package-release.ps1
scripts/package-beta-release.ps1
scripts/package-promotable-release.ps1
scripts/test-update-e2e.ps1        升级 E2E 测试
build/installer/                   13 个已发布版本 0.1.12 → 0.1.23
```

这是一条**跑了 13 个版本、经过实战的 Windows 发布与升级链路**。

而 `OTA升级架构设计.md` §9 自己写了：

> 现有 HQDroidDeck `runInstaller` 使用 Inno Setup 参数，**不能原样用于 Tauri NSIS/MSI**。可复用 Updater 主流程，但必须为不同安装器实现独立参数、退出码和回滚策略。

也就是说，**选 Tauri 就等于主动放弃这条链路，另起一套 NSIS**，文档已经把这笔账记下了。选 Wails 则可以沿用 Inno Setup（Inno 支持 `PrivilegesRequired=lowest` 做当前用户级安装，能满足 P0 要求的 `%LOCALAPPDATA%\Programs\HQAgent-Hub` + 无 UAC），HQUpdateKit 的 `InstallerStrategy` 在 Windows 侧只需一种实现而不是两种。

**这是我在资料里找到的、最实在的一条支持 Go 的论据**，而且是文档自己承认的成本。

## 5. 逐维度对比

| 维度 | Tauri 2 / Rust | Wails v2 / Go | 谁占优 |
| --- | --- | --- | --- |
| Windows 构建前置 | 需 MSVC Build Tools（~2-3 GB，一次性） | 无 | **Go** |
| macOS/Linux 构建前置（Phase 3） | Xcode CLT / gcc+webkit2gtk | 同左（需 cgo） | 平 |
| 手机端 | 移动端一等公民，但**已被排除出选型考量** | 无移动端 | 不适用 |
| 语言栈 | Python + **Rust** + Go + TS（四种） | Python + Go + TS（三种） | **Go** |
| HQUpdateKit 复用 | 独立进程，与壳语言无关 | 同左 | 平 |
| HQDroidDeck 壳代码复用 | 不可复用 | Windows 上可抄，Phase 3 失效 | 弱 Go |
| 发布/安装链路 | 需另建 NSIS，文档已承认成本 | 可沿用 Inno Setup + 13 版实战脚本 | **Go** |
| WebView 安全模型 | Tauri 2 capability/permission 细粒度体系，W5 已用 `capabilities/default.json`；CSP 可配置性强 | Wails v2 无等价体系，靠 WebView2 默认策略 + 自建约束 | **Tauri** |
| 框架活跃度 | Tauri 2 当前主线，活跃 | Wails v2 维护期，v3 长期 alpha | **Tauri** |
| 现有代码沉没成本 | 2478 行 Rust，**从未编译过，已验证价值为零** | 需重写 | 平（切换窗口期） |
| 前端影响 | 无 | 仅 `getHubEndpointFromTauri()` 几十行，**且已在 R1 必修清单里要重写** | 平 |
| 协议包影响 | 无 | 无（`runtime-descriptor.json` 语言中立，Go DTO 早已生成） | 平 |

## 6. 结论与建议

### 用户关心的两个维度，答案是

- **手机端**：已由用户排除出选型考量，技术栈开放（PWA / 原生 Android / Flutter）。Tauri 的移动端优势在本项目归零。副产物：若走 Flutter/Kotlin，`packages/protocol` 需新增语言目标（约一天，W0 的 Phase 2 待办）。
- **跨平台**：不构成换 Go 的理由。Go 免工具链只在 Windows 成立，Phase 3 到 macOS/Linux 时两边成本一样；而且 HQDroidDeck 的 Windows 专用壳代码那时也失效。

### 真正的取舍是这两条

**选 Go/Wails 的理由**：省掉 Windows 上一次性的 MSVC 安装；四语言降到三语言；沿用 HQDroidDeck 跑了 13 版的 Inno Setup 发布链路（这条文档自己承认 Tauri 要另付成本）；那 2478 行 Rust 从没编译过，现在切换沉没成本为零。

**选 Tauri 的理由**：Tauri 2 的 capability/permission 体系对一个「能改文件、能跑 shell、能推 git」的产品是实打实的纵深防御，Wails v2 没有等价物；框架活跃度明显更好，Wails v3 长期 alpha 是真实的生态风险；既有五份文档已把 Tauri 写进制品表、安装策略和前端技术栈，切换要回改一批文档。

### 我的建议

**这是个没有明显优势方的决策，两条路都能走通。** 如果一定要我给倾向：

按你提出的两个维度（跨平台 + 技术路线）来判断，**它们其实都不支持换**——手机端是平的，跨平台是平的甚至微弱不利。真正支持换的是发布链路复用和语言栈收敛，那是**工程便利**层面的，不是**技术路线**层面的。

而反对换的两条里，**Wails v3 长期 alpha 的生态风险**是我最在意的：这个产品要做 OTA、要商业发布、要 Phase 3 跨平台，押在一个维护期框架上，三年后的迁移成本会比现在装一次 Build Tools 大得多。

所以：**倾向留在 Tauri，装 Build Tools。** 但如果你的判断是「一期就是自用，先跑起来最重要，三年后的事三年后说」，那换 Go 也完全站得住——尤其是发布链路那条，能省掉一整套 NSIS 的重建。

### 无论选哪条，这些是不变的

- W1 Local Hub（Python）已完成可合，不受影响
- W4 前端已过 F1，可继续 F2/F3/F4，F0–F4 全程 Mock 不依赖桌面壳
- `packages/protocol` 语言中立，不受影响
- 五进程边界、hub.json 契约、Bearer + WS Ticket 鉴权模型不变
- HQUpdateKit 仍是独立 Go 模块，两个产品共用
