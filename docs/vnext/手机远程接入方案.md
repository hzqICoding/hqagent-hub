## 1. 产品定位

**HQAgent-Hub 的远程能力是一个通信工具**：解决人不在电脑前时，没法和自己电脑上的 Agent 会话沟通的问题。

- 服务端只做三件事：**认证、设备配对绑定、消息与状态的中转和暂存**。
- 全程不参与 AI 的订阅、安装、分发和调用。用户用哪家 Agent、用什么账号，由用户自己在电脑上安装和登录。不用这个工具，用户的 Agent 照样能用；用了，只是多了一个手机上的入口。
- 登录和扫码绑定，绑的是「这台手机可以操作我那台电脑」这层关系，和任何 AI 服务无关。
- 目标用户是已经会用 Claude Code、Codex 这类工具的人，不面向新手。

### 1.1 由定位推出的设计约束

| 约束 | 说明 |
| --- | --- |
| **服务端不调用模型** | 一切模型调用都发生在用户电脑上的 Worker 里。技术方案 §3 中「Model Provider：可选轻量识别/视觉预处理」若要做，只能做成 Worker 侧插件 |
| **服务端不保存模型凭据** | Claude/Codex 等的登录状态、API Key 留在用户电脑上，不进服务端、事件或日志 |
| **后续模型类扩展放在 Worker 侧** | 如接入 DeepSeek 等，做成 Worker 插件，由用户填自己的 Key；不做服务端共享能力 |
| **如实报告** | 面向懂行的用户，出错时直接给真实原因（退出码、stderr、越界路径），不包装成模糊提示 |

## 2. 总体结构

```text
   H5（主渠道）    飞书机器人（便利入口）    小程序体验版（高风险审批）    群机器人（通知）
        │ HTTPS/WSS         │ 长连接                    │ HTTPS/WSS                ▲ Webhook
        ▼                   ▼                           ▼                          │
  ┌──────────────────────── Hub Server（阿里云，已备案域名）─────────────────────────┐
  │  Channel 层：WebChannel ｜ FeishuChannel ｜ NotifyChannel                          │
  │  ───────────────────────────────────────────────────────────────────────── │
  │  核心（沿用 vNext）：账号 / 设备配对 / Conversation / Command / Outbox / 事件投影 │
  │  存储：SQLite WAL（经仓储层访问）；附件与产物：OSS 私有 Bucket                   │
  └──────────────────────────────────────────────────────────────────────────────┘
                                         ▲
                                         │ Worker 主动建立 WSS：/ws/v2/worker
                              用户电脑上的 Worker（执行全部在这里发生）
```

**Channel 只是入口和出口，核心不因渠道而改变。** 飞书里的一条消息到了服务端，和 H5 发来的一条消息是同一种东西：一条 user message 加一个 Command。

Worker 主动向外连接，用户电脑不需要公网 IP、端口映射或内网穿透。

## 3. 部署（阿里云）

服务器和域名已在阿里云大陆完成 ICP 备案，直接使用。

| 组件 | 选择 | 说明 |
| --- | --- | --- |
| 规格 | 2 核 2G 起步 | 服务端不跑任务、不调模型，只转发和暂存，负载很轻 |
| TLS | Caddy 或 Nginx 终结 TLS | 应用监听 `127.0.0.1:8080`，与技术方案 §3.2 一致 |
| 应用 | Hub Server，FastAPI 单进程 | 首版单进程写库 |
| 数据库 | SQLite WAL | **所有访问经仓储层**，业务代码不写 SQLite 特有语法；用户增多后迁阿里云 RDS PostgreSQL 只改仓储层 |
| 附件与产物 | OSS 私有 Bucket，预签名 URL 直传直取 | 截图、APK 不走 WebSocket，也不占服务器带宽 |
| 备份 | SQLite Backup API 生成一致性快照，定期传 OSS | 不复制正在写入的库文件（技术方案 §9） |
| 网络 | 安全组只开 443 | SSH 限定来源 IP，或只用阿里云控制台远程连接 |

**不要**把已备案域名解析到境外服务器。备案与接入商绑定，指向接入商以外的服务器，可能导致备案被注销。

### 3.1 自部署

服务端必须能由用户自己部署（Docker 镜像或一条命令）。自己运营的那一台和别人自部署的是**同一份代码**。

对这类用户来说，自部署是一个真正的卖点：懂行的用户在把电脑执行权交给别人的服务器前会犹豫，自部署让代码和对话只经过他自己的服务器。

## 4. 接入渠道

| 渠道 | 定位 | 状态 |
| --- | --- | --- |
| **H5** | **主渠道**。完整界面，复用现有 Vue 组件；也是唯一不受第三方平台限制、能随用户规模扩展的渠道 | R1 建设 |
| **群机器人 Webhook** | 单向通知：审批待处理、任务完成、失败 | R2 建设。飞书自定义机器人、企业微信群机器人、钉钉自定义机器人均**不需要企业认证** |
| **飞书自建应用（长连接）** | 自己和团队的便利入口，在飞书里直接对话派活 | R3 建设。**前提待实测**，见 §10 |
| **微信小程序** | 体验版自用，承担高风险审批（见 §6） | R4 建设。**不提审上线** |
| 企业微信双向对话 | — | 暂不做：接收消息需配置回调域名，存在主体一致要求，个人备案难以满足 |
| Android APK | — | 不做：需要安装、不跨平台 |

### 4.1 Channel 层规则

- **幂等键用平台消息 ID。** 飞书在超时时会重复投递事件，不去重就会重复派发同一条任务（对应 vNext 验收 E01）。
- **一个飞书话题对应一个 Conversation。** 在话题里回复是继续对话，新开话题是新任务。
- **审批用消息卡片按钮**，点击产生 approval decision，仍由 Worker 做最终校验和消费。
- **长代码、diff 不塞进 IM 消息。** 卡片只放摘要，附跳转 H5 的深链。
- 渠道身份（飞书 open_id 等）只用于把消息归到对应用户，不替代服务端账号。

### 4.2 小程序的限制

- 只作体验版，把自己和团队加为体验成员使用；体验成员有人数上限。
- 订阅消息是一次性的，每推送一条都需要用户先授权一次。通知仍以群机器人为主。
- 小程序没有 DOM，现有 Vue 组件不能直接复用；可复用的是 store 逻辑和协议类型。

## 5. 配对与多用户

### 5.1 配对

沿用接口与插件协议 §3：Worker 生成设备凭据 → 服务端返回短期配对码 → 用户在已登录的手机上确认 → Worker 用设备凭据建立 WSS。

配对的含义只有一个：**这个账号可以向这台电脑发送命令。** 设备凭据独立于浏览器会话、本机 Hub Token 和任何模型凭据，可以随时撤销。

### 5.2 多用户（从 R1 第一天起就按多用户做）

即使一开始只有一个用户，也按多用户实现。事后给没有租户字段的库补隔离，是最容易出越权漏洞的地方。

- 服务端所有业务表带 `owner_id`，所有查询按它过滤。
- 一台 Worker 只属于一个 owner；服务端只把该 owner 的 Command 投递给它。
- 用户之间的 Conversation、消息、附件、事件投影完全隔离。
- 首版不做团队共享（多人操作同一台电脑）。需要时另行设计。

### 5.3 对话以服务端为准

配对之后，**对话以服务端记录为准**，电脑界面也通过服务端提交消息。这与讨论共识 §1「手机和电脑操作同一份任务对话」一致，也是 IM 渠道的必然要求：飞书里的对话天然在服务端。

这调整了技术方案 §3.1 的 `authority=local/remote` 双轨设计：配对后新建的对话一律为 remote。未配对时（纯本地使用）保持现有本地模式不变。

电脑断网时，已在执行的任务按技术方案 §5.3 在本地权限内继续；受影响的只是**发送新消息**。

### 5.4 离线消息策略

**电脑离线时，手机发出的命令在服务端排队**，电脑上线后按 `conversationSeq` 顺序投递。这正是服务端存在的意义：关掉手机不影响任务，电脑离线时指令不丢。

界面必须显示「电脑离线，指令已排队」，不能显示成「执行中」。排队的命令可以在投递前撤回，规则见接口与插件协议 §4.1。

## 6. 审批安全分级

服务器被攻破时，不能让攻击者借此操作用户的电脑。多用户场景下，被攻破的服务器会波及**所有**已配对的电脑，这条因此是必须项。

关键在于：**只要客户端代码由我们的服务器下发，客户端上的任何校验都能被服务器绕过**（攻击者改掉下发的 JS，就能让手机「替你」批准）。

| 渠道 | 谁能伪造批准 | 可批准的动作 |
| --- | --- | --- |
| 电脑本机 | — | 全部 |
| 小程序 | 代码包由微信托管和签名，**不是我们的服务器下发的**，可在本地持有密钥签名 | 全部（R4 起） |
| H5 | 服务器被攻破即可 | 仅低风险 |
| 飞书卡片 | 服务器被攻破，或飞书账号被盗 | 仅低风险 |

**高风险动作**：`git_push`、`deploy`、`delete`、`db_migrate`，以及 Worker 策略另行声明的动作。R4 之前，这些动作只能回电脑上批准。

**小程序签名审批（R4）**：配对时小程序生成密钥对，公钥登记到 Worker，并在电脑上核对指纹确认。审批时对 `(attemptId, 动作哈希, 过期时间)` 签名，Worker 用登记的公钥验签，服务端只转发。

Worker 侧的权限策略（角色白名单、路径校验、审批消费）是最后一道防线，**不因为命令来自已认证的服务器就放松**。

## 7. 附件与产物

- 手机上传截图：先向服务端申请 OSS 预签名上传 URL，直传 OSS，再把附件 ID 随消息提交。
- Worker 按附件 ID 取用，校验大小和哈希（对应 vNext 验收 E14）。
- 产物（如 APK）由 Worker 上传到 OSS，手机通过有时效的预签名 URL 下载。下载链接必须指向实际产物（讨论共识 §7）。
- 附件保留时长、单个大小上限、每个用户的配额：R1 开工时确定。

## 8. 原生会话

用户所说的「和自己的会话对话」，很可能也包括**他在终端里直接开的** Claude Code / Codex 会话，而不只是通过本工具创建的会话。

vNext 已把「原生会话发现、读取、导入」列在 N1 第 4 条（验收 E11）。按本文定位，这项能力的优先级应当提前。**是否提前，待用户确定。**

安全边界沿用 E11：可以读取历史，但不能在外部会话仍然活跃时无条件启动第二个写进程。

## 9. 推进顺序

| 步骤 | 内容 | 出口 |
| --- | --- | --- |
| **R1** | 服务端核心：账号、配对、Worker WSS、Command/Outbox、事件投影、离线排队；`owner_id` 多用户隔离；H5 手机布局与 RemoteGateway；自部署打包 | 讨论共识 §8 验收场景 1–4、6 在 H5 上通过 |
| **R2** | NotifyChannel：群机器人推送审批待处理、完成、失败 | 手机不打开页面也能及时知道有事要处理 |
| **R3** | FeishuChannel：长连接机器人，话题对应对话，卡片审批低风险动作 | 在飞书里完成「派任务 → 看进度 → 批准 → 继续」 |
| **R4** | 小程序体验版：本地密钥签名审批，放开高风险动作的远程批准 | 高风险动作在手机上批准，Worker 验签通过 |

R1、R2 与渠道选择无关，可以直接开工。R3 开工前先完成 §10 的实测。

## 10. 待确认事项

| 事项 | 为什么重要 | 关闭方式 |
| --- | --- | --- |
| 飞书免费版能否创建自建应用并启用**长连接接收事件** | R3 的唯一前提；这条路可以绕开回调域名验证，但未经实测 | 在飞书开放平台建一个自建应用试开长连接 |
| 飞书免费版 API 调用月配额 | 决定 R3 能否长期使用 | 以飞书当前政策为准 |
| 日常主要用飞书还是企业微信 | 企业微信的双向消息绕不开回调域名主体一致问题 | 用户确定 |
| 原生会话能力是否提前 | 见 §8 | 用户确定 |
| 小程序体验成员人数上限 | 决定 R4 能覆盖多大的团队 | 以微信公众平台当前规则为准 |
| 附件保留时长、大小上限、配额 | 见 §7 | R1 开工时确定 |

首版不做端到端加密。对自部署用户影响很小（数据只经过自己的服务器）；对使用他人运营服务器的用户，需要在界面上明确告知。
