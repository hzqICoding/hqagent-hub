## 1. 目标与建设范围

面向个人开发者：手机或电脑发送自然语言与附件，连接已登录 Agent 的开发电脑，在指定项目内持续分析、开发、验证和交付。不同角色可以选择不同运行时、模型和推理等级；所有执行都由 Worker 统一管理。

核心场景：新建“Q20 地面站项目开发” → 定位 ua_android → 梳理 RTK → 现场发截图要求修复 → 查看结果 → 再发消息要求打包上传 APK → 获取链接并现场反馈。

首个试用版本先在本机验证这条链路的核心部分：选项目 → 选场景和角色方案 → 对话分析/规划/修改 → 查看结果 → 继续同一任务。暂不建设公网服务端和手机连接。“本地”不意味着云模型无需网络。

### 1.1 分阶段范围

| 阶段 | 必须完成 | 不作为该阶段前置 |
| --- | --- | --- |
| N0-A 执行基础 | 真实 TaskService 的去重、结果状态、审批、续接和取消；明确任务/会话边界 | 云部署、完整桌面安装、完整 OTA |
| N0-B 本地试用版 | 本地聊天；项目/任务/会话选择；场景模板；角色职责、Agent/model/effort配置；只读分析、规划、编码与按需复核 | 轻量前置模型必装、远程账号、设备配对、插件市场、动态任意DAG |
| N1 首个远程版本 | 一个账号、一台活动 Worker；手机 Web；项目选择/定位；直接分析和编码；进度、审批、取消、继续会话；断线补传 | 多人协作、跨设备迁移任务、第三方插件市场 |
| N2 场外验证闭环 | 截图/日志附件；可选规划角色；修复、构建、产物上传、下载校验和现场验证记录 | 全自动硬件验证、应用商店发布、任意 GUI 自动化 |
| N3 扩展与交付 | 更多模型连接、更多 Worker、逐平台安装验收、可选桌面与 OTA | 是否商业化另立需求 |

Windows/macOS/Linux 的协议与核心接口从 N0 起保持兼容；每个平台的“已支持”状态必须由实际测试证明。Android 构建等能力按节点工具链开放，不能把平台兼容与所有插件可用混为一谈。

### 1.2 默认交互

- 本地版默认“本机”，先选项目、任务或已有会话，输入描述即可；角色、路径范围和模型参数收进高级设置。远程版再增加设备选择。
- 新建任务只保存标题与上下文，不立即启动所有模型。
- 明确的暂停、取消、进度查询由程序处理；项目能直接匹配时不调用意图模型。
- 模糊目录描述才进入轻量定位 Agent；复杂需求才调用规划者；简单任务可直接交给执行者。
- 本轮成功代表本轮执行完成。Bug 修复成功与用户现场验证通过分别记录。

## 2. 技术选择及取舍

| 项 | 选择 | 理由 |
| --- | --- | --- |
| 前端 | 保留 Vue 3、TypeScript、Vite、现有组件与 Gateway；先补生产本地聊天入口，后增 RemoteGateway | 已有页面可复用；先看真实协作效果 |
| Worker | 保留 Python、asyncio、FastAPI 本地入口和 SQLite | 现有核心资产可继续用，主要缺应用层接线 |
| 服务端 | N1 再建 Python/FastAPI 模块化单体；N0 不部署独立 Server | 本地业务入口与 Worker 同进程，远程接口保留扩展边界 |
| 数据库 | Worker 独立 SQLite；服务端首版单进程 SQLite WAL | 自部署组件少；多副本服务端不在首版范围，届时单独迁移 PostgreSQL |
| 通信 | N0 为回环 HTTP/WS；N1 公网 HTTPS/WSS | 本地无需域名、VPS或设备配对；远程不另造执行内核 |
| 插件 | 随产品发布的受信插件清单、注册表和可选受管子进程 | 具备扩展边界，不先建设市场和热更新 |
| 桌面/更新 | 保留 Tauri/Rust 与 Go 更新资产，作为独立可选交付线 | 不阻塞远程功能，也不产生一次语言重写工程 |

相比全部改成 TypeScript，目前方案迁移范围小。本地试用先验证角色与对话执行效果，完整桌面/OTA及手机远程都不阻塞该验证。Python/Node 的精确构建版本、锁文件和安装包依赖在 N0 环境复现中固定，不在本文凭空升级库版本。

## 3. 进程、部署与状态归属

首版只需要下面两个运行部分：

```text
本机浏览器 / 可选现有桌面入口
             ↓ 本地 Gateway
Python Worker（嵌入本地 Conversation/Command 入口）
  ├─ 场景与角色方案、聊天和任务记录
  ├─ TaskEngine / RunSupervisor / SQLite
  └─ Claude Code、Codex 等内置执行器
```

本地 Conversation/Command 入口与 Worker 同进程部署，复用领域接口，不另启动一个“假云端”。云端队列、设备凭据、跨节点事件投影和复制Outbox不属于 N0 实现要求；本地消息去重、事件和会话持久化仍需具备。

以下为 N1 远程模式的目标结构，按阶段启用：

```text
手机 / 电脑浏览器
  ├─ HTTPS：登录、命令、历史、附件
  └─ WSS：订阅服务端事件
          ↓
Hub Server：账号、设备配对、Conversation、Command、附件入口、事件投影
          ↕ Worker 主动连接 WSS
Worker / Local Hub：TaskEngine、RunSupervisor、审批、原生会话、项目和产物
  ├─ Runtime 插件：Claude Code / Codex
  ├─ Model Provider：可选轻量识别/视觉预处理
  └─ Capability 插件：项目发现 / Android Builder / Artifact Uploader

可选 Tauri：作为本机客户端和托盘入口，复用同一个 Worker。
```

### 3.1 唯一写入者

下表描述远程模式。N0 中 Conversation、消息、场景配置和 Command 由 Worker 内嵌的 LocalConversationService/CommandHandler 写入本机 SQLite；TaskEngine 的唯一执行权保持不变。

| 事实 | 权威来源 | 另一端的职责 |
| --- | --- | --- |
| 账号、配对关系、Conversation、用户消息与 Command 入队 | 服务端 | Worker 消费经过认证的消息 |
| 本机项目路径、CLI 环境、原生会话与登录凭据 | Worker | 服务端保存允许展示的索引 |
| Task/Run/Node/Attempt 执行状态与执行计划 | Worker TaskEngine | 服务端按事件构建只读投影 |
| 进程是否运行、取消是否成功 | Worker Supervisor/执行器回执 | 服务端展示已知状态及观察时间 |
| 审批请求、失效与实际消费 | Worker ApprovalBroker | 服务端传递用户决定，不自行放行 |
| 文件是否完整、构建来源、产物校验 | 持有文件的 ArtifactStore | 传输副本校验通过后更新对应副本状态 |

服务端不得根据“断线”推断任务失败，不自行创建重试 Attempt，也不把模型文本解析为数据库终态。规划 Agent 提出任务计划，TaskEngine 校验并执行。

Conversation 必须记录 authority=local/remote。以后接远程时，既有本地记录可按原 ID 导入为历史快照，不能重放历史 Command。活跃对话不自动切权威源；完成当前执行后显式交接，转为 remote 的对话连本机界面也通过 RemoteGateway 提交新消息。首版不做云/本地双主同步。

### 3.2 部署与数据目录

- N0 由 Worker 提供同源静态 Web 和业务 API，仅监听回环地址；本地认证见协议的“本地运行模式”。不依赖 VPS、远程账号或设备配对。

- 服务端逻辑地址：`https://<hub-host>`；反向代理终结 TLS。应用默认监听 `127.0.0.1:8080`，端口可配置；首版仅一个应用进程写服务端 SQLite。
- 浏览器 API：`/api/v2/*`；浏览器事件：`/ws/v2/client`；Worker 主动连接：`/ws/v2/worker`。
- Worker 本机入口保留回环监听；不把现有本机 Token 或原始 CLI 控制端口暴露公网。
- Worker 默认数据路径：Windows `%LOCALAPPDATA%/HQAgent-Hub`；macOS `~/Library/Application Support/HQAgent-Hub`；Linux `${XDG_DATA_HOME:-~/.local/share}/hqagent-hub`。允许明确覆盖，三平台实现由 PlatformServices 管理。
- 首版开发者可在已有 Python 环境运行；普通用户交付需要打包 Worker 运行时及启动入口，不能把“源码可运行”当成“安装即用”。
- 供应商登录与密钥留在执行电脑；安装为当前用户服务或登录项，检测实际启动环境中的 CLI/工具链。
- 服务端保存消息、被上传的附件与允许同步的结果；可包含用户主动提交的代码/日志。第一版不宣称端到端加密。

## 4. 核心数据模型

| 实体 | 定义与关键关联 |
| --- | --- |
| Project | 逻辑项目，例如 Q20；可关联多个机器上的 Workspace |
| Workspace | Worker 上的已授权路径/仓库，包含 workerId、rootPath、VCS；worktree 是它的执行 checkout |
| Conversation | 长期聊天容器，关联 Project/当前 Task；保存消息顺序及默认执行方案 |
| Task | 长期目标，例如 RTK 重连 Bug；可由多个用户轮次逐步完成 |
| Run | 一次用户要求产生的执行轮次，例如分析、修复、构建；固定输入和配置快照 |
| Node | Run 内一个步骤，类型为 agent 或 capability，可有前置依赖 |
| Attempt | 某 Node 的一次真实执行尝试；每次重试新建，保留之前结果 |
| AgentSessionBinding | 业务对话/角色与原生 session/thread 的精确映射及来源 |
| Artifact | 输入截图、日志或输出报告、APK；包含内容哈希、大小、来源与副本 |
| Command | 用户操作的持久化消息，有目标 Worker 和幂等键；控制命令不自动新建 Run |

### 4.1 关系规则

- “Q20 地面站项目开发”可以作为 Project 和默认 Conversation 的显示标题。用户不必理解内部实体数量。
- 第一条执行消息如未指定 Task，Worker 建立 Task 并回传绑定事件；后续按明确 Task 继续。远程模式创建Conversation不要求Worker在线；本地模式需要Worker运行，页面关闭不影响已接任务。
- 每条用户消息都有 messageId；需要执行的消息关联 Command，再由 Worker 创建 Run。一个执行 Command 最多产生一个对应 Run；取消/暂停只控制已有 Run，终态后的人工重试按下述规则产生关联的新 Run。
- 服务端事务为需要执行的用户消息分配 conversationSeq；助手回复、纯控制命令不占用该序列。同一对话的执行消息按该顺序入队；取消/审批可指向当前 Run，不必等待普通消息执行完。
- 追加业务要求创建下一 Run，复用 Task 和符合条件的 AgentSessionBinding。Run 尚未终态时，受策略允许的重试创建新 Attempt；已终态 Run 不重新改回 running，用户 retry 创建带 retryOfRunId 的新 Run，复用已核实输入/产物并保留旧结果。
- 新任务不按 workspace+role 全局复用原生对话，避免不同任务串上下文。
- Task 只有用户明确结束或完成约定验收才关闭；单轮 Run 成功不自动关闭长期目标。

### 4.2 两端最小持久化

N0 单份本地存储增加 projects、conversations、messages、commands，与 Worker 执行表共同使用本机 SQLite；不建远端复制表。

N1 服务端：users、devices、projects、conversations、messages、commands、command_outbox、worker_event_inbox、execution_projection、artifacts/replicas。

Worker：workspaces、tasks、runs、nodes、attempts、agent_sessions、command_inbox、events、approvals、artifacts、execution_profiles、workspace_locks。N1再增加跨端events_outbox及确认游标。

迁移时优先扩展现有表；这些是逻辑职责，不要求机械新建同名表。原生历史仍由各 CLI 保存，Hub 保存索引、运行规格和必要交接资料，不能只备份一个 session ID。

## 5. 状态、调度与故障恢复

### 5.1 状态口径

| 对象 | 状态与解释 |
| --- | --- |
| Command | queued → accepted → completed/failed；接单前可 rejected；delivered 只作为传输观测，不代表已接单 |
| Run | queued、running、waiting_input、waiting_approval、pause_requested、paused、cancel_requested、succeeded、failed、cancelled、recovery_required |
| Node | pending、ready、running、waiting_input、waiting_approval、succeeded、failed、cancelled、blocked |
| Attempt | prepared、starting、running、succeeded、failed、cancelled、outcome_unknown |

成功需要执行器明确终态、结果校验通过和必需产物就绪。长驻 App Server 不必退出才能成功；其 turn 终态是依据。CLI Job 则核对进程退出、结果与残留子进程。异常 EOF、超时或响应丢失不等于完成。

pause 只在 Node 边界生效；运行中消息默认排队到下一 Run。首版不承诺冻结任意工具调用或无损中途换模型。cancel 先进入 cancel_requested，核实受管执行停止后才 cancelled；停止结果不明进入 recovery_required。

### 5.2 幂等与事务

下列两端流程适用于 N1；N0 将第1、2步合并为本地消息/Command/待执行 Run 同事务提交，不先实现跨机通信和双端复制。持久化后启动外部进程、真实结果核实与事件一致性的要求相同。

1. 服务端将用户消息、Command 和派发 Outbox 原子保存后返回 202。
2. Worker 按 commandId 去重，在本地事务保存 Inbox、待执行 Run/控制动作和接单回执。
3. Supervisor 从已提交的执行意图启动 Attempt；数据库事务内不等待模型或网络。
4. 状态变化与本地事件/Outbox 同事务提交。服务端接收事件去重后，投影与浏览器投递游标同事务更新。
5. 崩溃发生在“外部进程启动”和“启动确认落库”之间时，先核实 executionId、PID+启动时间、原生 turn/session 与文件状态。结果不明时不自动再执行写入或发布。

同 key 不同请求内容返回冲突；断网补发不产生新 Attempt。可安全重试的操作由插件声明，发布等副作用必须核实目的端现状。

### 5.3 离线与接管

- Worker 失联后，已接单任务可以在本地权限和已有审批范围内继续；需要新的远程输入时等待。
- 服务端显示“离线；最后已知状态”，新指令排队，不把任务转给另一台电脑。
- 设备在线状态/连接 epoch 不是文件锁。Worker 用本地数据库锁及执行所有者记录控制同一 Workspace、原生 Session 的并发。
- 首版不自动跨 Worker 迁移执行。跨机器恢复需要源码/工作区、会话存储、凭据和执行能力全部满足，不能仅凭原生 ID。
- 事件 seq 沿用现有本地数据库单调递增设计；数据库身份用 workerStoreId，进程实例用 workerEpoch。重启不重置 seq；恢复旧备份/重建库需更换 storeId，进行快照对账。
- storeId 变化后清空当前世代的确认游标，并暂停旧的未决命令自动重投，先对照服务端接单记录与本机 Attempt 核实。确认游标绑定 workerId+workerStoreId，旧库 ack 不得裁剪新库 Outbox；本地 Inbox 回滚也不允许重新执行旧副作用。

## 6. Agent、角色与原生会话

### 6.1 执行方案

角色描述职责；runtime 描述 Claude Code/Codex 等执行方式；model/effort 描述实际模型配置；provider/authProfileRef 是可选连接信息，不能强制所有原生 CLI 暴露统一供应商账户结构。

配置优先级：本轮显式覆盖 → Task 固定方案 → Conversation/Project 默认 → 用户默认。Run 启动时记录 resolved model、effort、插件版本、权限与工作区；运行期间不跟随全局配置变化。

缺省模型可以继承所选 Runtime 的当前配置，但启动时必须尽可能解析、记录实际值。快照区分 requestedModelId/requestedReasoningEffort 与 resolvedModelId/resolvedReasoningEffort；实际值无法解析则为 null、显示 unknown，不冒充请求型号。明确指定的模型/effort 不可用时返回能力缺口，不静默替换。

默认提供两种模式：直接执行；规划后执行。复核按任务方案启用。轻量 intake 仅在模糊意图/目录定位时调用，不作为每条消息必经步骤。

本地试用首批三个场景模板：

| 场景 | 默认分工 | 交付 |
| --- | --- | --- |
| 代码分析 | 一个分析角色，选择 Claude 或 Codex，只读 | 带源码依据的逻辑梳理 |
| 需求规划 | 一个规划角色；用户可后续明确要求实施 | 方案、范围、验收条件 |
| 开发修复 | 执行角色；按方案选配规划/复核角色 | 改动、验证结果和剩余事项 |

用户可编辑每个角色的职责提示词、Runtime、具体模型/effort和受限工具。职责提示词不能扩大权限；技能资产通过明确配置加载，不假定子进程会继承人工CLI的全部技能。首版角色组合使用可配置模板，任意自动生成DAG留待实际需要。

页面优先提供“项目/任务列表、聊天与进度、当前场景/角色设置”三部分；用户输入普通描述时无需手写结构化任务包。默认模板使用已安装Agent，DeepSeek等额外前置连接按需配置。

### 6.2 会话目录与续接

- 分别声明 list/read/adopt/resume/attach_active 能力，不能用一个 supportsResume 代替。
- list/read 只发现当前节点和用户能访问的历史；adopt 建立 Hub 索引，保留来源和原生 ID。
- 历史可见不表示可以接管仍在独立终端运行的会话。状态未知时只允许查看，待执行结束或明确完成接管后续接。
- 同一原生会话同时只有一个活跃 Attempt；锁键包含 workerStoreId、runtime 数据目录标识及 externalSessionId。
- Claude 与 Codex 各维护独立会话；切换 Runtime 通过任务交接摘要/文件引用建立新会话。模型切换在 Runtime 支持且用户明确指定时可在下一轮发生，并记录差异。
- 原生会话不存在时显式报告；用户可选择依据交接资料新开会话，禁止静默假恢复。

## 7. 插件边界

| 类型 | 职责 | 第一批 |
| --- | --- | --- |
| agent_runtime | 调用完整 Agent、模型配置、会话、工具审批、输出及取消 | Claude Code、Codex |
| model_provider | 文本/图像推理、结构化输出与模型目录；不直接持有任意文件操作权 | 一个可配置的模型连接，按需启用 |
| capability | 确定性操作、环境探测、长 Job | Workspace Discover、Android Build、Artifact Upload |
| channel | 消息收发与通知 | 内置 Web；其他渠道后续 |
| workflow_pack | 角色提示词、技能和经校验的工作流模板 | 分析、修复、构建交付 |

第一版插件入口由受信清单注册。现有 AgentAdapter 可由兼容层包成内置插件，不强制立刻把全部旧实现搬到新进程。需要独立运行时或故障隔离的 Capability 通过受管 stdio JSON-RPC 子进程运行；两者遵守同一宿主接口。

插件不直接改核心数据库。宿主提供 TaskContext、授权的 Artifact 访问、进度发送和凭据引用；权限由宿主和操作系统/执行器共同执行。子进程隔离不是完整安全沙箱。

MCP 作为工具桥接插件；Skills 是工作指导资产，不拥有任务状态机。规划者的 submit/get/continue/cancel 工具一律进入 Worker CommandHandler。

插件升级仅影响新 Run；旧 Run 使用固定版本。首版不做第三方代码热加载、在线市场、任意依赖自动安装、插件自更新或任意 UI 扩展。

## 8. 项目发现、写入与构建交付

### 8.1 目录和新项目

先查已登记项目/别名/最近记录，再在用户允许的搜索根目录中有限遍历。返回候选及证据，Worker 核实真实路径；歧义通过 waiting_input 处理。自然语言“切目录”只改变当前业务上下文，不调用全局 chdir。

- read_only：允许非 Git 目录，按授权范围只读。
- code_change：已提交基线 + 隔离 worktree；读到的实际代码和分支要记录。
- project_bootstrap：用户明确要求新建项目时，可在已授权父目录中创建指定空目录；检查不存在/为空、无符号链接越界后，由确定性操作执行 git init 和空初始提交，再建立隔离写工作区。新项目成果通过显式集成步骤写回目标分支。非空既有目录不自动初始化/提交。
- build：使用本次修复的明确 CodeSnapshot，冻结期间禁止其他写入；构建输出放在受控路径。

Bootstrap 属于新增能力，不意味着解除旧 D38 或既有危险动作授权。具体操作形成可审查计划；用户当前命令可以提供所需范围授权，不能扩大到父目录其他项目。

### 8.2 截图 → 修复 → APK

截图首先形成完整、已校验的 Artifact，保留原图；Runtime 支持图像时直接提供引用。不支持则明确选择可用视觉处理，输出文字分析与原图引用，并记录这种降级；不能静默丢图。

修复 Run 保存 CodeSnapshot：baseCommit、worktree、补丁与新增文件清单及哈希、来源 Run。存在未提交改动时，单独的 commit SHA 不能充当完整代码版本。

用户后续发“打包并上传”才产生交付 Run：

1. 选定修复产物快照和构建 profile，锁定来源。
2. Builder 检查 JDK/SDK/Gradle/签名引用，执行参数化构建，不把手机文本拼成 shell 命令。
3. 校验 APK 包名、版本、签名摘要、大小和 SHA-256，登记 Artifact。
4. Uploader 仅消费该 Artifact 与已配置 destinationId；授权绑定具体目标和内容哈希。
5. 目的端确认文件完整且下载可用后产生链接；超时先查目的端，不盲目再次发布。
6. 回传变更、测试覆盖与未验证内容；现场验证由用户反馈记录。

审批可消费已明确授权的动作，不要求每个正常步骤重复确认；动作参数、产物或发布目标变化需重新判定授权。

## 9. 权限、账号与运维边界

本机用户隔离、路径和执行权限从 N0 保留。以下远程账号、设备配对及双端备份条目到 N1 才启用；本地认证使用协议§1.1，不要求为单机试用先建设云账号体系。

- 首版单一所有者账号，浏览器会话使用 HttpOnly/Secure Cookie；同源 WS 校验 Origin，HTTP 写操作有 CSRF 防护。具体登录密码由初始化流程创建，无默认公开密码。
- Worker 配对需要已登录所有者确认一次性配对请求；设备凭据独立于浏览器会话、本机 Hub Token和模型供应商凭据，可撤销。细节见协议草案。
- Shell、外网访问、上传等操作先与执行 profile 和具体用户授权匹配；未覆盖动作进入审批。角色/插件不能通过自然语言扩大自身权限。
- 审批决定绑定 attempt/action/参数哈希/目标/内容哈希及有效期，Worker 最终校验并幂等消费；失效决定不能唤醒旧工具请求。
- 用户决定已保存、Worker 正在传递决定、执行器已接受分别记录。服务端收到批准不意味着工具已经放行；回执不明时进入待核实，不能盲目再次批准/发布。审批消费完成也不等于对应操作执行成功。
- WebSocket 帧不传 APK 或图片二进制。附件有配额、MIME/内容检查、哈希确认和路径隔离。
- 服务端与 Worker 分别使用 SQLite Backup API/一致性备份；不能复制正在写入的数据库文件冒充可恢复备份。事件裁剪须保留快照与对账口径。
- 发布失败或设备离线不删除本地产物；凭据、完整环境变量及供应商认证文件不得进入事件和普通日志。

## 10. 现有资产迁移原则

1. 先记录并保护 integration 的未提交修改，再形成可复现代码基线；本轮没有代替用户提交或合并。
2. 保留现有 Adapter/RoleResolver/Session/Worktree/存储基础，集中改造真实 TaskService 及状态所有权。
3. v1 本机接口先保持兼容；v2 业务对话与远程接口新增，不把同名 v1 Task 字段悄悄改成 Run。
4. 旧 Task 迁移成一个历史 Task + legacy Run/Attempt 映射，缺失配置和状态标为 unknown/需核实，不猜测补全原生会话。
5. 移动界面与桌面通过 Gateway 分离认证和连接方式；生产环境禁止默认使用 MockGateway。
6. 协议/schema/DTO 进入实施时仍走单一生成链；不用本目录的 JSON 示例替代正式 Schema。
7. Tauri/Go 更新模块暂保留，后续按独立验收线接回；不在此轮删除资产或修改其他产品。
