## 1. 适用范围与版本

本文件是拟定契约，不表示端点已经实现。既有 `/api/v1`、协议包 0.2.x 和 Adapter Port 保持原语义；v2 设计通过 W0 评审后再写入 `packages/protocol`，不得让调用方各自创建同名兼容 DTO。

- 本地版 Base URL：`http://127.0.0.1:<worker-port>/api/v2`；远程版为 `https://<hub-host>/api/v2`，各自同源 Cookie 认证。
- JSON 使用 camelCase；状态使用 snake_case；时间为 UTC RFC3339 字符串；ID 为不可猜测的标识符。
- 请求体不接收任意 executable、shell 字符串或服务器本地路径。运行目标由 workspaceId、profileId、destinationId 等受控标识解析。
- 每个写请求使用 `Idempotency-Key`；绑定所有者、操作资源与规范化请求哈希。同 key/同内容返回同一资源；同 key/不同内容返回 409。
- 202 表示命令及投递意图已持久化，绝不表示 Agent 已完成。
- 错误包含 code/message/requestId/retryable，必要时有缺失能力与可选恢复动作；不返回凭据。
- 示例状态与 ID 仅为格式演示，正式 Schema 由协议包唯一生成。

### 1.1 本地运行模式（N0）

- Worker 嵌入 LocalConversationService/CommandHandler并提供本地静态Web；聊天、场景配置、消息和执行状态存同一本机SQLite。调用相同领域服务，不模拟一条Server↔Worker网络链。
- 本地Web使用本地Gateway，202表示本机命令已持久化；targetWorkerId默认本机，设备列表可用单节点描述，不建设云端配对。
- Worker/托盘向当前用户展示短时一次性本地配对码；`POST /auth/local-session`核实后设置HttpOnly、SameSite=Strict Cookie。回环HTTP不强行使用只适合HTTPS的Cookie配置；远程HTTPS启用Secure。本地仍校验Host/Origin/CSRF并限制错误尝试。
- 本地配对码不是Hub Token，不放进URL；现有Hub Token不进入网页响应体或前端存储。已有Tauri v1入口可并存，不能通过生产页面打包VITE_HUB_TOKEN来绕开本地认证。
- N0只实现Conversation/Message、项目/方案、Command/Run、审批和本机事件等当前所需端点。设备远程注册、双端Outbox/投影、上传中转和公网订阅留到N1/N2。
- 对话记录authority=local/remote，每个对话同时只有一个消息排序和命令入口。后续启用远程不重放历史消息为新任务，不对运行中的本地对话自动切换权威源。

后续§3–4中描述的服务端配对、网络投递和确认语义属于N1目标，不是本地试用版的依赖。

## 2. 浏览器 API 最小集合

| 方法与路径 | 语义 | 主要响应 |
| --- | --- | --- |
| POST /auth/local-session | N0：一次性本机配对码换本地浏览器会话 | Cookie；无远程账号 |
| POST /auth/login；POST /auth/logout | 建立/注销所有者浏览器会话 | Cookie；不向 JS 返回长期 Token |
| GET /devices | 节点、最后在线时间、能力版本 | 列表与 observedAt |
| GET /projects；GET /workspaces | 已同步的逻辑项目与本机工作区索引 | 不宣称离线节点路径仍存在 |
| POST /conversations | 建立空业务对话及默认项目/方案 | 201 conversation |
| POST /conversations/{id}/messages | 保存用户消息并创建 execute/append Command | 202 messageId、commandId |
| GET /conversations/{id}/messages | 分页读取已保存的聊天和回报 | opaque cursor |
| POST /runs/{id}/commands | pause/resume/cancel/retry 控制 | 202 commandId |
| POST /commands/{id}/cancellations | 撤回尚未形成可见 Run 的请求 | 202；未派发可终止入队，派发结果不明时交 Worker 核对并取消 |
| GET /commands/{id}；GET /runs/{id} | 查看接单与执行投影 | observedAt、workerOnline、实际状态 |
| GET /execution-profiles；PUT /execution-profiles/{id} | 编辑角色方案，版本递增 | profileVersion；不改变运行中快照 |
| POST /history/queries | 请求 Worker 列出/读取原生历史 | 202 commandId；历史结果按页回传 |
| POST /history/adoptions | 将外部历史与业务对话绑定 | 202；Worker 验证后完成 |
| POST /approvals/{id}/decisions | 提交批准/拒绝决定命令 | 202；Worker 决定是否仍然有效 |
| POST /artifacts/uploads | 创建上传会话、检查配额 | 201 uploadId 与相对上传路径 |
| PUT /artifacts/uploads/{id}/content | 上传二进制内容 | 暂存完成；不代表 Artifact 就绪 |
| POST /artifacts/uploads/{id}/complete | 校验长度/哈希并登记 | 201 artifactId 或 409/422 |
| GET /artifacts/{id}；GET /artifacts/{id}/content | 查询元数据、鉴权下载 | 200；外部分享链接另行配置 |
| GET /events?after={cursor} | 补拉可见事件，必要时提示快照 | items、nextCursor |
| GET /snapshots/{scope} | 会话/任务投影快照 | snapshotCursor |

上述控制接口不能由 HTTP Handler 直接开进程。所有副作用统一经 CommandHandler 和 Worker 的 TaskEngine。分页返回有界数据，不一次把所有 CLI 历史读到内存。

### 2.1 新消息示例

```

```

首次消息尚无 Task/Run 时不伪造执行 ID。Worker 接单后产生 task.bound/run.created 事件；查询 Command 可找到对应资源。

## 3. Worker 配对与连接

首版使用独立设备 Bearer 凭据，通过 TLS 传输；它不是供应商 API Key、本机 Hub Token 或浏览器 Cookie。

1. Worker 在本机生成高熵设备凭据并安全保存；向服务端建立有时效的待配对请求。服务端仅存凭据验证值，不在响应体或日志回传原始凭据。
2. 服务端返回 pairRequestId、短期配对码和有效期。Worker 显示设备名与服务端地址。
3. 用户在已登录 Web 中输入/扫描配对码，核对设备并确认。配对码仅用于关联，不能直接执行任务。
4. Worker 使用设备凭据建立 WSS 连接。服务端校验归属、撤销状态、协议和 pending pairing 是否完成。
5. 设备可以被所有者撤销。运行中任务不因网络撤销自动假定已停止，界面提示需本机处理；后续云命令拒绝投递。

配对端点需限速与短期过期；设备凭据只在首次登记/认证需要时传输，经 TLS 且禁止日志采集。浏览器不读取本机 Hub Token。

Worker hello 最小字段：workerId、workerStoreId、workerEpoch、protocolVersion、platform、architecture、capabilityRevision、lastServerAck（含 workerStoreId、seq，未确认时为 null）。服务端返回协议协商结果、连接 ID、待投递命令游标和带 storeId 的事件确认位置。旧世代 ack 不得作用于新世代。

心跳初始默认 15 秒；45 秒未收到标为连接失联。该状态只影响路由/显示，不释放本机 Session/Workspace 锁，也不导致跨节点重派。

## 4. 命令、回执与事件

### 4.1 下行命令

```json
{
  "protocolVersion": "2.0-draft",
  "commandId": "command-001",
  "messageId": "message-001",
  "conversationId": "conversation-q20",
  "conversationSeq": 1,
  "targetWorkerId": "worker-pc",
  "type": "run.submit",
  "createdAt": "2026-09-24T01:00:00Z",
  "expiresAt": null,
  "payload": {
    "taskId": null,
    "workspaceId": "workspace-ua-android",
    "text": "梳理 RTK 基站的代码逻辑",
    "attachmentIds": [],
    "executionProfileId": "profile-direct",
    "profileVersion": 1
  }
}
```

Worker 对 commandId 唯一去重，并校验 conversationId、目标节点、资源权限与请求哈希。重复命令返回已有 receipt，不重新建 Task/Run。过期命令落 rejected，不能重新解释为新消息。

执行消息必须附 conversationSeq（服务端仅为需要执行的用户消息分配，助手回复和纯控制命令不占用），Worker 按该顺序排队；缺口先补齐，不因网络先到就抢跑后一句。控制命令引用目标 Run/Command，独立于普通执行队列。撤回与派发需事务协调：只有确认未进入派发的 Command 才能直接拒绝执行；发送后未收到回执属于结果不明，不能仅删除服务端记录当作取消成功。

已分配序号但撤回的执行消息保留跳过记录，并随缺口补传给 Worker，防止后续消息永远等待不存在的序号。首版同一 Conversation 的执行固定在一台 Worker；跨节点迁移须另立交接和游标起点，不能把单节点顺序协议直接用于迁移。

回执：commandId、status=accepted/rejected、workerStoreId、receivedAt、taskId/runId（若已创建）、error（若拒绝）。接单回执落库后才发送。

accepted 之后必须由 Worker 发出 command.completed 或 command.failed（含 resultRef/resultStatus 或 error），rejected 只表示接单前拒绝：

- execute/append：关联 Run 成功时 completed，执行失败时 failed；被取消时 completed 并明确 resultStatus=cancelled，界面仍显示 Run 已取消。
- pause/resume：对应控制动作实际生效时 completed，不等待整个 Run 最终成功。
- cancel：确认停止或原执行早已终态时 completed，结果不明保持未完成并显示 recovery_required，明确无法取消时 failed。
- retry：新的 Attempt 或 retry Run 已持久化入队时 completed，返回其 ID；后续执行结果由该资源报告。

纯查询/历史命令以结果页保存完成为终态。浏览器不能把 command.completed 一概显示为“开发任务成功”。

### 4.2 上行事件

```json
{
  "protocolVersion": "2.0-draft",
  "eventId": "event-001",
  "workerId": "worker-pc",
  "workerStoreId": "store-001",
  "workerEpoch": "boot-002",
  "seq": 108,
  "commandId": "command-001",
  "conversationId": "conversation-q20",
  "taskId": "task-rtk",
  "runId": "run-analyze",
  "nodeId": "node-read",
  "attemptId": "attempt-001",
  "type": "attempt.started",
  "occurredAt": "2026-09-24T01:00:02Z",
  "payload": {
    "runtimeId": "codex",
    "executionId": "execution-001"
  }
}
```

- seq 是每个 workerStoreId 的持久递增序列；workerEpoch 标识启动实例。重启保留 storeId 和 seq，防止与现有 Hub 事件设计冲突。
- 同 eventId 重传视为同一事件；同 storeId+seq 对应不同内容应拒绝并报告存储冲突，不能覆盖。
- 服务端只确认已持久化的连续序号。收到跳号事件可缓存或要求补拉，不能把最大已见序号当作连续确认点。
- Worker 保留未确认 Outbox；服务端投影按事务处理事件去重和更新。浏览器使用独立 opaque serverCursor，不直接使用单台 Worker 的 seq。
- 数据库回滚、重建或从落后备份恢复时，必须更换 workerStoreId，并核对非终态任务；不能用旧 storeId 重新分配已经对外使用过的序号。
- storeId 改变时本地 lastServerAck 重置为 null，服务端冻结旧世代未决命令自动重投，等待接单/执行记录对账。新库缺少 command_inbox 不能成为重复执行旧命令的理由。
- 首版支持游标补传和快照重建，不承诺永久保存逐字输出。终态、审批、产物和关键错误不可被当作进度噪声丢弃。

事件最小集合：command.accepted/rejected/completed/failed、task.bound、run.created/state_changed、node.state_changed、attempt.started/progress/result、message.appended、approval.requested/decision_recorded/dispatching/consumed/denied/expired/delivery_unknown、artifact.ready、capability.changed。

### 4.3 控制语义

- append：保存新消息并排队下一 Run；不修改运行中 Attempt 的原始输入。
- pause：持久化意图，到 Node 边界才 paused。控制回执不能假装立即冻结进程。
- resume：解除明确暂停/等待条件后由 Supervisor 调度，不只改数据库标签。
- retry：Run 未终态时，按策略为没有仍存活执行的 Node 创建新 Attempt；Run 已终态时创建带 retryOfRunId 的新 Run，不翻转历史终态。发布/不明副作用先核实。
- cancel：进入 cancel_requested；受管进程树或原生 turn 确认停止后终态 cancelled。超时进入 recovery_required 并保留取消记录。

## 5. 角色与执行快照

配置分为请求 profile 与实际 RoleExecutionSnapshot。Run 固定 profile 版本；每个 Node 派发前解析实际 Runtime/Model，保存不可变快照。规划者动态增加节点仍受该 Run 已冻结的能力/预算/权限范围约束。

请求 profile 使用 modelId/reasoningEffort；实际快照字段为：snapshotId、roleId、runtimeInstanceId、requestedModelId、requestedReasoningEffort、resolvedModelId、resolvedReasoningEffort、providerId（可选）、authProfileRef（不可泄露的引用）、pluginVersion、hostApiVersion、workspaceId、permissionProfileId、requiredCapabilities、resolveSource、createdAt。

resolvedModelId/resolvedReasoningEffort 可为 null，并附 modelResolutionSource=explicit/runtime_default/observed/unknown 和 validationStatus=validated/unverified/unsupported。请求值不直接冒充实际值；已知不支持的明确配置不启动执行。

示例保留用户希望的配置组合，不声明目标机器已经支持：

```json
{
  "id": "profile-codex-dual",
  "version": 1,
  "roles": {
    "planner": {
      "runtimeId": "codex",
      "modelId": "gpt-6-astra",
      "reasoningEffort": "xhigh",
      "permissionProfileId": "plan-and-dispatch"
    },
    "executor": {
      "runtimeId": "codex",
      "modelId": "gpt-5.6-luna",
      "reasoningEffort": "max",
      "permissionProfileId": "isolated-code-change"
    }
  },
  "policy": {
    "onUnavailable": "report_capability_gap",
    "maxConcurrentAgentExecutions": 3
  }
}
```

调用前必须验证模型与 effort 组合。上限 3 包含等待子任务的主控 Agent 与其子执行会话；调度不得因主控占满名额造成死锁，必须保留可执行子任务的槽位或暂停主控执行回合。

## 6. 插件描述与运行接口

### 6.1 Manifest 最小草案

```json
{
  "pluginId": "hq.android-builder",
  "version": "0.1.0",
  "hostApiVersion": "1.0-draft",
  "kind": "capability",
  "trust": "builtin",
  "placement": "worker",
  "transport": "stdio-jsonrpc",
  "entrypoint": "bin/android-builder",
  "platforms": ["windows", "darwin", "linux"],
  "architectures": ["x86_64", "aarch64"],
  "operations": [
    {
      "name": "build-apk",
      "inputSchema": "schemas/build-input.json",
      "outputSchema": "schemas/build-output.json",
      "supportsCancel": true,
      "recovery": "inspect-only",
      "retrySafety": "reconcile-required"
    }
  ],
  "requiredHostCapabilities": ["process.spawn", "artifact.write"],
  "configSchema": "schemas/config.json"
}
```

这是插件格式示例，引用的脚本和 schema 在实现包中才会存在；platforms 是插件作者声明，宿主还需 probe 结果及验证记录，不能据此立即展示已验收。

- entrypoint 只能解析到安装包内受信入口，不接收任务随附脚本地址。支持平台专属入口和架构约束；清单不得下载并执行任意依赖。
- 注册表按 pluginId+version 管理已安装版本，健康状态为 available/degraded/unavailable，附原因。
- requiredHostCapabilities 是需求声明，授权由宿主决定。插件不能自授 shell/network/凭据权限。
- 第一版允许受信内置 Adapter 通过 inprocess 兼容层注册；它与 stdio 插件使用同一语义。外部第三方 inprocess 加载不开放。
- 正式 Manifest 使用 transport 判别联合：inprocess 必须给 builtinRegistrationKey，禁止外部代码入口；stdio-jsonrpc 必须提供按平台/架构匹配的 entrypoint/targets。平台和 architectures 必须共同校验，不能把一个架构的可执行文件发给另一个架构。上方是通用脚本入口示例，二进制包须改用 targets。
- PluginHost 提供受控工具和事件 API；插件不直连核心数据库，不持有浏览器或设备认证凭据。

### 6.2 JSON-RPC 与执行生命周期

stdio 使用逐行 UTF-8 JSON-RPC 2.0：stdout 仅协议，stderr 为经过脱敏的诊断。宿主以参数数组启动固定入口，设置 cwd、有限环境变量和平台进程管理。

```json
{
  "jsonrpc": "2.0",
  "id": "rpc-001",
  "method": "execute",
  "params": {
    "operation": "build-apk",
    "executionId": "execution-build-001",
    "attemptId": "attempt-build-001",
    "input": {
      "codeSnapshotId": "snapshot-fix-001",
      "buildProfileId": "q20-test"
    }
  }
}
```

execute 响应可以 completed+result，也可以 accepted+executionId。后者通过 execution.event 通知进度和终态。executionId 由宿主在启动前持久化，插件不得把重复执行请求视作新的副作用。

| 操作 | 约定 |
| --- | --- |
| initialize/describe | 协商 API 版本，返回操作及模型/历史/附件能力 |
| probe | 检查安装、登录、依赖和配置；不启动付费开发任务 |
| execute | mode=new/resume；resume 必须带 sessionBindingId，由宿主解析准确原生ID；输入输出由 operation schema 校验 |
| inspect | 返回 running/terminal/unknown，附实际观测依据；不是猜测进程名称 |
| cancel | 返回 requested/confirmed/failed；明确是否支持原生中断和进程树清理 |
| recover | 仅在声明支持时恢复/重新订阅；否则返回 recovery_unsupported |
| decide | 回传已核实且未过期的工具审批决定 |
| history.list/read/adopt | 可选、分页、有界；不会默认接管活跃独立 CLI |
| history.attachActive | 可选；核实原生执行身份和占用状态后接入现有执行。首版不支持的Runtime返回能力缺口，不能退化成新会话 |

进度事件至少含 executionId、pluginEventId、type、occurredAt、payload；宿主接收后分配规范的 Worker 事件序号。terminal 只能产生一次，重复终态返回同一结果；矛盾终态报错。最大单帧初始设为 256 KiB，超限内容转 Artifact。

### 6.3 旧 Adapter 映射

| 旧方法 | vNext 接入 |
| --- | --- |
| detect/health | describe/probe |
| start/resume | execute(mode=new/resume)，由完整持久化 RunSpec 重建上下文 |
| stream_events | execution.event 适配，不改变原生供应商事件协议 |
| approve | decide，经 ApprovalBroker 校验后调用 |
| cancel | cancel+inspect，直到明确终态 |
| collect_result | 经 schema 校验的终态结果，TaskEngine 决定上层状态 |

不强制认为旧 resume 已可靠；先修复返回 AdapterFailure 仍标 ACTIVE 的缺口。正式改动须由协议包生成新 DTO，经 Mapper 兼容，不复制旧类型。

### 6.4 分项能力

history.list/read/adopt/resume/attach_active，input.text/image/file，structured_output，approval.interactive，cancellation.turn/process_tree，recovery.inspect/reattach/resume 分别报告 supported/conditional/unsupported，并附 constraints/reason。

模型能力由所选 Runtime/Model 的交集决定，不按品牌推断。MCP工具是否可用、图片是否可读取，也必须由实际配置声明。

## 7. 原生会话引用

SessionBinding 至少保存 bindingId、conversationId、taskId、roleId、workerId、workerStoreId、runtimeInstanceId、runtimeDataRootRef、externalSessionId、workspaceId、profileSnapshotId、source、lastObservedAt、activityStatus。

- source 为 hub_created 或 adopted；activityStatus 可为 unknown，不能强制把列表项标 idle。
- history.read 获取的是供应商可访问的历史内容，不是终端窗口截图。
- 导入只创建可验证索引。adopt 请求引用先前 discovery 返回的 opaque nativeRef，不能让浏览器随意指定本机 transcript 文件路径。
- 续接读取持久化运行规格，并核实同一绑定没有其他活跃 Attempt；无历史/无权限/CLI仍在执行时明确拒绝或等待。
- 原生对话恢复不恢复文件系统快照，也不重启之前中断的任意 shell 命令。

## 8. 附件、产物与授权

ArtifactRef：artifactId、kind、mediaType、name、sizeBytes、sha256、state、sourceMessageId/sourceRunId、replicaId。传给插件时增加由宿主解析的短期只读访问句柄；跨设备协议不传可信任本地绝对路径。

ArtifactAccessRef 固定为 artifactId、mediaType、sha256、accessHandle、expiresAt。stdio 插件可通过宿主 `artifact.openRead(accessHandle)` 获取受限数据或受管临时文件，inprocess 使用等价宿主方法；两者都先校验归属、有效期和内容哈希。图片能力声明不代替实际读取通路。

上传状态：created → uploading → verifying → ready / rejected。只有 ready Artifact 可进入执行。中断上传可在保留期内按 offset 与内容哈希续传；默认先支持单文件顺序上传，不把分块并发当首版要求。

初始可配置限额：图片每张 20 MiB、每条消息最多 5 张；单文件产物 500 MiB；WebSocket 单事件 256 KiB。服务端与 Worker 启动时协商实际限额；磁盘不足时拒绝接收，不接受一半后误标 ready。

APK 元数据至少包含 packageName、versionName、versionCode、signerDigest、codeSnapshotId、buildProfileVersion、builderPluginVersion、sha256。下载 URL 只是可撤销/有时效的访问位置，不代替 Artifact 身份。

ApprovalRequest 至少绑定 approvalId、runId、nodeId、attemptId、externalRequestId（如适用）、action、argumentsHash、artifactHash（如适用）、destinationId、expiresAt。Worker 对同一决定幂等消费；批准记录不能用于不同参数、新 Attempt 或新 APK。

审批状态至少区分 pending、decision_recorded、dispatching、consumed、denied、expired、delivery_unknown：服务端保存用户决定只投影为 decision_recorded；Worker 校验并记录发送意图为 dispatching；原生执行器接受决定，或受控能力执行获得一次性授权后，才记录 consumed。消费记录包含所有绑定字段及回执依据，consumed 不等于动作成功。原生审批回执丢失时先 inspect/核实，不具备原生去重能力时不得盲目重送，记 delivery_unknown 并暂停相关步骤。重复决定返回已记录结果，不再次派发。

## 9. 错误与协议演进

最小错误类别：unauthenticated、forbidden、idempotency_conflict、worker_offline、capability_missing、model_unavailable、session_not_found、session_busy、session_recovery_failed、approval_expired、artifact_not_ready、artifact_hash_mismatch、execution_outcome_unknown、plugin_incompatible。

错误码名在正式协议冻结时与现有 registry 对齐；本文不会直接改动旧错误枚举。

追加可选字段可以兼容演进；改变状态语义、所有权、审批或 Run/Task 映射需显式协议版本迁移。未知可选进度事件可忽略但计数；未知终态/审批事件必须报协议不兼容，不能丢弃后宣称成功。

本协议进入实现的验收见 [实施与验收](实施与验收.md)，格式样例集中于 [contracts.json](examples/contracts.json)。
